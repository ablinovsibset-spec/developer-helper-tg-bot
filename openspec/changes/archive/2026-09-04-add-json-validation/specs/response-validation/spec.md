# response-validation Delta

## Purpose

Эшелонированная валидация структурированных (JSON) ответов модели: схема формата первым рубежом, валидатор в агентном цикле вторым, retry-with-feedback через историю для чинибельных провалов и немедленный терминал для нечинибельных.

## ADDED Requirements

### Requirement: Валидация структурированных ответов модели
Каждый структурированный (JSON) элемент ответа модели — аргументы вызова инструмента, а в будущем финальный ответ по схеме — SHALL валидироваться на синтаксис (разбор JSON) и соответствие ожидаемой форме (обязательные поля и их типы). Провал валидации SHALL возвращаться модели как сообщение с конкретной ошибкой (включая текст ошибки разбора) и указанием ожидаемого формата; агентный цикл продолжается.

#### Scenario: Некорректный JSON в аргументах инструмента
- **WHEN** модель возвращает вызов инструмента, чьи аргументы не разбираются как JSON
- **THEN** модель получает сообщение с текстом ошибки разбора и требованием корректного JSON-объекта, цикл продолжается

#### Scenario: Нарушение схемы аргументов
- **WHEN** аргументы вызова инструмента разбираются как JSON, но обязательный строкочный параметр отсутствует или не является строкой
- **THEN** модель получает сообщение о конкретном нарушении схемы, цикл продолжается

### Requirement: Retry через агентный цикл с фидбеком
При провале валидации структурированного ответа битый ответ SHALL оставаться в истории диалога, а следующий к нему — добавляться сообщение с конкретной ошибкой и требованием формата. Повторная попытка SHALL выполняться очередным вызовом LLM в рамках общего агентного цикла, без отдельного скрытого цикла перезапросов.

#### Scenario: Модель исправляет формат
- **WHEN** модель получила фидбек о сломанном JSON и повторный запрос контекста
- **THEN** в истории видны битый ответ и сообщение об ошибке, а следующий ход модели содержит корректный JSON

### Requirement: Отдельный предел подряд идущих провалов валидации
Провалы валидации SHALL считаться отдельным счётчиком подряд идущих неудач, не смешиваемым с общим лимитом шагов агентного цикла; успешная валидация SHALL обнулять счётчик. При достижении третьего подряд провала цикл SHALL прекращаться терминальным сообщением о неспособности модели сформировать корректный структурированный ответ, отличимым от сообщения об исчерпании шагов цикла.

#### Scenario: Третий провал подряд останавливает цикл
- **WHEN** три ответа модели подряд проваливают валидацию
- **THEN** цикл прекращается и пользователь получает сообщение о неспособности сформировать корректный ответ

#### Scenario: Успех обнуляет счётчик
- **WHEN** за двумя провалами валидации следует успешный ход, а затем ещё провал
- **THEN** счётчик подряд идущих провалов учитывает только один провал после успеха, цикл продолжается

### Requirement: Нечинибельный провал — обрыв по длине
Структурированный ответ, чей формат сломан обрывом генерации по лимиту токенов (finish_reason равен length), SHALL прекращать цикл терминальным сообщением сразу, без повторных запросов: фидбек не устраняет причину обрыва.

#### Scenario: Оборванный JSON не ретраится
- **WHEN** модель вернула JSON-ответ, оборванный лимитом длины (finish_reason = length)
- **THEN** дополнительные запросы к LLM не выполняются, пользователь получает терминальное сообщение об обрыве ответа

### Requirement: Схема формата ответа первым рубежом
Запрос к LLM, где ожидается структурированный ответ, SHALL включать указание схемы формата ответа (response_format), если поставщик его поддерживает. Отсутствие поддержки у поставщика MUST NOT вызывать сбой: запрос отправляется без схемы, корректность обеспечивается валидацией и retry-with-feedback.

#### Scenario: Поставщик поддерживает схемы
- **WHEN** запрос требует JSON-ответ и поставщик поддерживает response_format
- **THEN** запрос уходит с указанием схемы, и ответы поставщика ей соответствуют

#### Scenario: Поставщик без поддержки схем
- **WHEN** поставщик не поддерживает response_format
- **THEN** запрос уходит без схемы, невалидные ответы ловятся валидатором и исправляются retry-циклом
