## Context

Валидация аргументов инструментов уже существует внутри `execute_tool_call` (agent.py): некорректный JSON возвращается модели как tool-сообщение с ошибкой, цикл продолжается. Но: счётчика провалов нет (серия фейлов съедает бюджет 8 шагов и заканчивается безликим STEPS_EXHAUSTED), обрыв по `finish_reason=length` не различается, `response_format` контракт LLMClient не принимает. `AssistantTurn` уже несёт `finish_reason`. Мотивация — см. proposal.md (Why).

## Goals / Non-Goals

**Goals:**

- Единый механизм «валидация → фидбек → переделка» для любых структурированных ответов модели, с отдельным пределом и различаемыми терминалами.
- Опциональный `response_format` в контракте LLMClient с деградацией без падения.
- Точка расширения для валидации финального ответа (пока без потребителя).

**Non-Goals:**

- Перевод финальных ответов на JSON — потребителя нет, валидатор финала остаётся заглушкой.
- GBNF-грамматики и провайдер-специфичные механизмы за пределами `response_format`.
- Валидация reasoning-поля (в контракт не попадает).

## Decisions

### D1: Retry через внешний цикл, без внутреннего цикла и без обёртки LLMClient

Провал валидации = обычные сообщения в истории; следующий вызов LLM делает внешний агентный цикл. Отвергнутые альтернативы: внутренний `while invalid: retry` (не работает для tool-args — протокол требует tool-сообщение с тем же `tool_call_id`, получаем два механизма) и обёртка `ValidatingClient` над швом (не может синтезировать tool-сообщения, мутный контракт истории). Единый механизм корректен для tool-args и естественно распространяется на финальный контент: фидбек для него — user-сообщение с ошибкой рядом с битым assistant-ответом.

### D2: Валидаторы как явные точки в цикле

Из `execute_tool_call` JSON-разбор и проверка схемы аргументов выносятся в обобщённый валидатор: `(ToolCall, ToolSpec) -> ошибка | None` (синтаксис + обязательные строковые параметры). В цикле агентa добавляется вторая точка — `validate_final(content) -> ошибка | None`, пока всегда «валидно»: при появлении первого потребителя финального JSON меняется только её реализация, каркас не трогается. Тексты ошибок: конкретная ошибка разбора + требование ожидаемой формы (мелкие модели чинятся лучше от конкретики).

### D3: Отдельный счётчик — 3 подряд, сброс успехом, свой терминал

`MAX_JSON_RETRIES = 3` подряд идущих провалов валидации; любой успешно провалидированный ход обнуляет счётчик. Достигнут — терминальное сообщение «модель не смогла сформировать корректный структурированный ответ» (отличимо от STEPS_EXHAUSTED, чтобы диагностировать причину). Ретраи по-прежнему едят общий бюджет 8 шагов — ранний выход по JSON-счётчу защищает от выжигания бюджета и уточняет диагноз, а не отменяет общий лимит.

### D4: Обрыв по длине — терминал без ретраев

Порядок проверки: сначала валидация, потом `finish_reason`. Если структура невалидна И `finish_reason == "length"` — терминальное сообщение об обрыве ответа сразу, без повторных запросов (фидбек не чинит лимит генерации). Валидный JSON при `length` (оборвался хвост, не структура) принимается.

### D5: response_format в контракте, деградация пробой с кэшированием

`complete(..., response_format=None)` в протоколе LLMClient; openai_compat пробрасывает в payload. Деградация: первый запрос с ненулевым `response_format`, получивший HTTP 400, повторяется без поля, а факт «поставщик не поддерживает» кэшируется в клиенте до конца жизни процесса. Альтернатива — флаг окружения `LLM_SUPPORTS_RESPONSE_FORMAT`: отвергнут, ещё одна ручка для одного провайдера. Вызывающий код пока не передаёт `response_format` (потребителя нет) — механизм проложен и покрыт тестами.

### D6: Тесты на scripted-фейках LLM

Существующий паттерн тестов с фейковым LLMClient расширяется сценариями: серия битых JSON-аргументов; битый → валидный (сброс счётчика); оборванный length; 400 от провайдера при response_format. Живая модель для ручной проверки: одна и та же сессия с json_schema и без — замер, не подавляет ли tool-calling.

## Risks / Trade-offs

- [`response_format` подавляет tool-calling у мелких моделей (Llama-3.2-3B)] → при появлении потребителя применять схему только к запросам без инструментов (финальный шаг) и сверять на живой модели (задача в tasks.md).
- [Фидбек-сообщения пухлят контекст] → тексты ошибок короткие, счётчик жёсткий (3), битый ответ остаётся одним сообщением.
- [Терминальные сообщения duplicated-логики] → обе константы сообщений живут рядом в agent.py, как STEPS_EXHAUSTED.

## Migration Plan

Чистое изменение кода, миграции данных нет. Изменение пользовательски видимое: новое терминальное сообщение при серии провалов валидации (раньше — сообщение об исчерпании шагов). Откат — вернуть код, контрактные изменения совместимы (параметр опционален).

## Результаты ручной проверки (задача 4.2)

Сверка на живой модели в LM Studio (temperature 0, один и тот же запрос с инструментом exec): `response_format: json_schema` в присутствии tools полностью подавляет tool-calling — модель перестаёт вызывать инструменты и сразу возвращает финальный JSON.

- `gpt-oss-20b` (текущий LLM_MODEL): без схемы — вызов exec в 3/3 попыток; с json_schema — 0/3 вызовов, finish_reason=stop, валидный JSON с текстом-обещанием вместо действия.
- `llama-3.2-3b-instruct`: без схемы — exec в 2/2; с json_schema — 0/2 вызовов.

Вывод: риск из Risks подтверждён на обеих моделях. При появлении потребителя финального JSON применять `response_format` только к запросам без инструментов (финальный шаг агентного цикла), не к шагам с tool-calling.
