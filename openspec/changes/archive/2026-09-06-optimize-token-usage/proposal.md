## Why

Аудит Части 2 (task/observability-2-baseline.md) показал: 67% входных токенов —
повторно отправленная информация, system prompt занимает 89.8% символов
контекста, `exec` даёт 92% токенов вывода инструментов (файлы читаются `cat`
целиком), а кэш промпта не работает — точная дата/время в начале системного
промпта ломает префикс на каждом сообщении. Часть 3 задачи observability
требует минимум 3 оптимизации, −30% стоимости и успех-рейт не хуже −2%.

## What Changes

- Новый инструмент `read_file(path, offset, limit)`: нумерация строк,
  жёсткий потолок ответа (~1500 символов), подсказка «продолжай со строки N»;
  описание `exec` больше не поощряет чтение файлов через `cat`.
- Компакция tool-выводов внутри прогона: символьный бюджет (~8k) на суммарные
  результаты инструментов; при превышении старейшие сворачиваются в заглушку
  «обрезано, было N символов, команда X — вызови повторно при необходимости».
- Кэш-дружелюбный префикс: дата/время уходит из системного промпта в
  контекстную строку рядом с текущим user-сообщением; префикс
  «reasoning + скиллы + история сессии» становится байт-стабильным между
  прогонами (правка требования skills-спеки).
- Benchmark-харнесс: опция `--label` (разделение baseline/optimized в одной
  БД) и автоматические проверки ответов сценариев (verbose — сумма 4 501 500;
  multiturn — три языка шага 1; files — упоминание бага).
- Отчёт до/после: цель −30% доказывается по сырым input-токенам; рядом —
  эффективная стоимость с кэш-скидкой по конфигурируемому прайсу
  (cached_tokens).
- Протокол «после»: 3 прохода харнесса с меткой `optimized` (21+ прогонов);
  baseline (2 прохода, метка `benchmark`) не перегоняется.

## Capabilities

### New Capabilities

- `read-file-tool`: постраничное чтение файлов в песочнице с лимитами в коде —
  альтернатива `cat` через `exec` для снижения токенов вывода инструментов.

### Modified Capabilities

- `skills`: требование «Текущие дата и время в системном промпте» меняется —
  дата/время (точность до минуты, обновление на каждое сообщение) остаются,
  но переезжают из system-сообщения в контекстную строку рядом с текущим
  user-сообщением ради стабильного кэшируемого префикса.
- `agent-loop`: результат инструмента по-прежнему попадает в контекст, но
  удерживается в рамках символьного бюджета прогона — старейшие выводы
  сворачиваются в заглушку с командой и размером.
- `benchmark-harness`: метка прогона становится параметром CLI (вместо
  фиксированной) + новое требование автопроверок ответов сценариев.
- `token-audit`: рядом с сырыми входными токенами аудит показывает
  эффективную стоимость с учётом кэш-скидки (конфигурируемый прайс
  cached_tokens); цель −30% считается по сырым токенам.

## Impact

- `src/dev_helper_bot/tools.py` — спецификация и реализация `read_file`;
  правка описания `exec`.
- `src/dev_helper_bot/agent.py` — компакция tool-выводов (бюджет, заглушки).
- `src/dev_helper_bot/skills.py` — сборка промпта без даты/времени; новая
  контекстная строка рядом с текущим сообщением.
- `src/dev_helper_bot/main.py` и `scripts/obs-benchmark.py` — общий шов сборки
  контекста (сейчас дублируется), метка и автопроверки в харнессе.
- `scripts/obs-audit.py` — кэш-скидка в отчёте.
- Сценарий `multiturn` опирается на память о шаге 1 — компакция dialog-истории
  НЕ входит в скоуп (риск для success rate).
- Риск: если тройка не даст −30% по сырым токенам — добавляем четвёртую
  оптимизацию (резерв — lazy skills через спайк-проверку на gpt-oss-20b).
