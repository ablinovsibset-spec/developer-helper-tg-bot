## Context

См. proposal.md — Why. Исходное состояние: контекст запроса собирается в двух
местах (`main.handle_text` и `Harness.process_message` в scripts/obs-benchmark.py,
дублирование), дата/время — строка 2 системного промпта с точностью до минуту
(skills.py `datetime_line`), tool-выводы append-only в пределах прогона
(agent.py), файлы читаются `cat` через `exec` (OUTPUT_LIMIT 3000 симв.),
`estimate_cost` биллит cached_tokens по полной входной цене, метка бенчмарка —
константа `BENCHMARK_LABEL`. Baseline зафиксирован: 14 прогонов, метка
`benchmark` (task/observability-2-baseline.md).

## Goals / Non-Goals

**Goals:**
- −30% входных токенов на прогон по сырым данным телеметрии (метки
  `benchmark` vs `optimized`) при падении успеха не более 2%.
- Все три оптимизации — с поведением, проверяемым автопроверками харнесса.

**Non-Goals:**
- Компакция dialog-истории (user/assistant) — сценарий multiturn опирается
  на неё; вне скоупа.
- Lazy skills (get_skill) — резервная четвёртая оптимизация, только если
  тройка не даст −30%.
- Реальная экономия денег: локальная LLM, стоимость виртуальная.

## Decisions

### D1. read_file — отдельный инструмент, лимиты в коде
Спецификация + реализация рядом с exec в tools.py; строки с номерами,
потолок ответа 1500 симв. (≈1/2 текущего OUTPUT_LIMIT exec), обрыв — с
подсказкой «продолжай со строки N». Чтение — тем же CommandExecutor
(одна песочница, `sed -n 'A,Bp' file` с перенумерацией или чтение файла
через docker cp — на усмотрение реализации, контракт один). Описание exec
прямо отговаривает от `cat` больших файлов.
Альтернатива — промпт-стимулирование sed/grep без нового инструмента —
отвергнута: лимиты гарантирует код, не дисциплина gpt-oss-20b.

### D2. Компакция tool-выводов: символьный бюджет, старейшие вперёд
Бюджет 8000 симв. на сумму содержимого tool-сообщений прогона (константа в
agent.py). После добавления новых результатов, если сумма превышает бюджет,
старейшие tool-contents заменяются заглушкой «[компакция: вывод обрезан,
было N симв.]». Команда вызова НЕ дублируется в заглушке: она остаётся
в соседнем assistant-сообщении с tool_calls, которое не компактируется.
Порог выбран из baseline: средний ход 8 без компакции ≈ 4.2k input-токенов,
из которых tool-выводы ≈ 33% ≈ 1.4k токенов ≈ 5.5k симв. — бюджет 8000
сворачивает только аномально разросшиеся прогоны (verbose-сценарий).
Альтернативы — свёртка по возрасту ходов (режет зря короткие прогоны) и
«только большие выводы» (сложнее правило, тот же эффект) — отвергнуты.

### D3. Дата/время — контекстной строкой в текущем user-сообщении
Строка «Текущие дата и время: …» добавляется в начало content текущего
user-сообщения (после загруженной истории), не персистится в память и не
попадает в системный промпт. Внутри прогона — неизменна (сообщение уже в
истории), между прогонами — свежая. Префикс «system + история сессии»
становится байтово стабильным.
Альтернатива — system-сообщение в конце списка — отвергнута: немонолитная
роль system в середине списка нестандартна для OpenAI-совместимых API.
Альтернатива — загрубить до даты — отвергнута: ломает точность «до минуты»,
требование сохранено, выигрыш меньше.

### D4. Сборка контекста — один шов
`build_system_prompt` (без даты/времени) + новая функция сборки запроса
(история + контекстная строка + user-текст) — единая точка в skills.py,
используемая и `handle_text`, и `Harness.process_message`. Дублирование
текста промпта в харнессе устраняется самим фактом шва.

### D5. Кэш-скидка — на стороне отчёта, телеметрия не трогается
`estimate_cost` остаётся сырой (история не переписывается при смене прайса).
Эффективная стоимость считается в obs-audit.py: cached_tokens × отдельный
прайс (CLI-флаг, по умолчанию 0.25 × входного) + остальные входные × входной.
Цель −30% — только по сырым входным токенам.

### D6. Протокол «после»: метка + автопроверки + 3 прохода
`--label optimized` в харнессе (по умолчанию — прежняя константа), автопроверки
по сценариям (verbose: «4501500» в ответе; multiturn шаг 3: три языка шага 1;
files: упоминание сути бага фикстуры), 3 прохода = 21+ прогонов. Baseline
не перегоняется. Сравнение: obs-audit по двум меткам + отчёт до/после
(task/observability-3-отчёт, по образцу baseline-файла).

### D7. Сверка кэш-данных LM Studio — первым шагом
Спайк: один запрос к живому LM Studio, inspect usage.prompt_tokens_details.
Если cached_tokens не отдаётся — кэш-эффект в отчёте помечается «данные
недоступны» (спека token-audit это разрешает), на цель −30% не влияет.

## Risks / Trade-offs

- [LM Studio не отдаёт cached_tokens] → кэш-скидка недоступна, метрика
  справочная; спайк D7 закрывает вопрос до реализации отчёта.
- [Модель продолжает читать файлы через cat] → правка описания exec;
  benchmark `files` проверяет фактическое поведение: если read_file не
  выбирается — стоп-факт для отчёта, а не молчаливый регресс.
- [Компакция заставляет перечитывать → лишние ходы при MAX_LLM_STEPS=8] →
  перечитывание через read_file дёшево (потолок 1500); автопроверки ловят
  провал сценариев; baseline уже имел 1/14 steps_exhausted — сравниваем
  статусы честно.
- [Перенос даты/времени меняет поведение скиллов, ожидающих время в промпте
  (morning/habr)] → строка остаётся в каждом запросе, меняется только место;
  автопроверки подтверждают.
- [LLM-недетерминированность на 21+ прогонах] → выводы по порядкам величин,
  как принято в проекте (baseline, design D-notes аудита).

## Migration Plan

Изменения атомарны в рамках PR: read_file и компакция включены константами
(потолок, бюджет) — откат точечной правкой константы; перенос даты/времени
и шов сборки контекста — чистый рефакторинг формата запроса без миграции
данных. БД телеметрии и памяти не меняют схему.
