# Design: add-agent-observability

## Context

Агентный цикл (`agent.py`) вызывает `llm.complete()` до 8 раз на сообщение; ответ
поставщика содержит `usage`, но `_parse_turn` его отбрасывает. Инструменты
проходят через единственную точку — цикл агента (валидация → исполнение →
результат в историю). Память уже использует паттерн «aiosqlite + WAL +
VM-локальный диск, владение lifecycle у main». См. proposal.md — Why.

## Goals / Non-Goals

**Goals:**

- Полная трасса токенов/стоимости/таймингов каждого прогона без изменения
  поведения агента.
- Данные, достаточные для аудита итерации 2 (в т.ч. `messages_count`,
  `prompt_chars`, raw usage JSON, label).

**Non-Goals:**

- Оптимизации, аудит, бенчмарк, success rate (следующие итерации).
- Ротация/очистка БД телеметрии; `/stats`-команда боту.
- Prompt-caching управление и измерение эффекта кэша llama.cpp.

## Decisions

### D1. Usage проходит через контракт хода, а не мимо него
`AssistantTurn` расширяется опциональным полем `usage` (nullable-поля
input/output/cached/reasoning + raw JSON ответа поставщика). Альтернатива —
обёртке разбирать сырой HTTP-ответ — отвергнута: дублирует клиент и ломает шов
`LLMClient` (обёртка работает с любым поставщиком, а не только с
OpenAI-совместимым).

### D2. Обёртка-декоратор + recorder, владельцем которого является обработчик
`ObservingClient` реализует протокол `LLMClient`, делегирует вложенному клиенту
и пишет телеметрию. `RunRecorder` создаётся на каждое сообщение в `handle_text`,
знает `run_id` и считает вызовы: turn_number = порядковый номер `complete()` в
прогоне (цикл зовёт `complete` ровно раз за итерацию — отдельный счётчик в цикле
не нужен). Итоговый статус прогона проставляет `run_agent` для терминальных
возвратов; ветка `LLMUnavailable` финализируется в `handle_text`. Альтернатива —
contextvars без изменения сигнатур — отвергнута: неявное состояние сложнее
тестировать, явный параметр проще.

### D3. Инструментация инструментов — в цикле агента
Точка записи — место формирования tool-сообщения в цикле: известны имя, размер
аргументов, размер результата, длительность исполнения и исход (в т.ч. отказ
валидации — «ошибка» с нулевой длительностью). Альтернатива — обёртки над
`CommandExecutor`/`HistorySearcher` — отвергнута: теряет валидационные отказы и
неизвестные инструменты, требует трёх обёрток вместо одной точки.

### D4. Хранилище — отдельная SQLite, паттерн memory.db
`obs.db`: aiosqlite, WAL, открывает/закрывает main (как `MemoryStore`), путь —
`OBS_DB_PATH`, дефолт `~/.local/share/dev-helper-bot/observability.db`
(VM-локальный диск — та же причина, что у памяти: сетевая ФС ломает локи/WAL).
Таблицы: `runs` (run_id, chat_id, label, started/finished, status, агрегаты),
`llm_calls`, `tool_calls` (FK на run). Каждая запись обёрнута в try/except с
логированием — best-effort. Альтернатива JSONL — отвергнута: дашборду нужны
агрегации.

### D5. Стоимость считается на записи и хранится с записью
Прайс — `OBS_PRICE_INPUT_PER_M` / `OBS_PRICE_OUTPUT_PER_M` ($ за 1M токенов);
кэшированные токены — по цене входных. Расчёт на момент записи: смена прайса не
переписывает историю. Стоимость виртуальная (локальная модель реально $0) —
учётная величина для сравнения «до/после».

### D6. Токены результатов инструментов — оценка chars/4
Никто не отчёсит токены tool-вывода; честный вклад измеряется в input_tokens
следующего LLM-вызова. Для атрибуции «топ инструментов» достаточно константы
~4 символа/токен. Токенизатор-библиотека — новая зависимость — отвергнута.

### D7. Dashboard — отдельный CLI-скрипт, синхронное чтение
`scripts/obs-dashboard.py` (sqlite3, read-only, бот не нужен): режим агрегатов
(`--label`, `--since` фильтры) и режим timeline (`--run <run_id>`). Формат —
по образцу задания: сводка + последовательность «Turn N LLM / tool» с токенами
и длительностями.

### D8. Схема БД толерантна к неполному usage
Колонки токенов nullable; рядом — raw usage JSON поставщика. Что отдал поставщик
— то заполнено; absence ≠ 0 (0 = «провайдер сказал ноль»). Это же правило — в
спеке llm-provider.

## Risks / Trade-offs

- [LM Studio не отдаёт cached/reasoning-токены] → поля null, dashboard выводит
  «недоступно» вместо нуля; raw JSON позволит доизвлечь без миграций.
- [Телеметрия добавляет задержку] → записи мелкие, WAL, best-effort; latency
  LLM-вызова меряется строго вокруг `complete()`.
- [Рост obs.db] → без ротации (осознанно); очистка — удалением файла при
  остановленном боте, документируется в README.
- [Race переупорядочивания записей] → monotonic-порядок не критичен: у записей
  timestamp и автоинкрементные id.

## Migration Plan

Новых миграций нет: obs.db создаётся при старте. Откат — убрать обёртку из
сборки main; файл БД остаётся инертным. Существующая memory.db не затрагивается.
