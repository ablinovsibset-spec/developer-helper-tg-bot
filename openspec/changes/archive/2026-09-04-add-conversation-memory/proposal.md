## Why

История диалога живёт в памяти процесса (`ChatHistories` в main.py) и умирает при каждом рестарте бота — а рестарты регулярны: `scripts/sbx-start.sh` после каждого ребута хоста пересоздаёт процесс. Пользователь возвращается на следующий день, а бот начинает с чистого листа; спросить об итогах прошлых бесед невозможно в принципе.

## What Changes

- Персистентное хранилище переписки на SQLite; файл живёт на VM-локальном диске сандбокса (не в workspace-маунте), переживает рестарты бота и паузу сандбокса, стирается только полным сбросом VM.
- Новая сущность «сессия»: `/new` закрывает текущую сессию и начинает новую; прошлые сессии сохраняются в БД и остаются доступны для поиска.
- В БД пишутся только сообщения пользователя и финальные ответы ассистента; инструментальный транскрипт (вызовы exec и их вывод) в БД не попадает.
- Непрерывность: при обработке сообщения контекст открытой сессии восстанавливается из БД — in-memory словарь удаляется, БД становится единственным источником истории.
- Новый инструмент агента `search_history`: поиск по прошлым беседам текущего чата, чтобы модель могла отвечать на вопросы «что мы обсуждали…».

## Capabilities

### New Capabilities

- `conversation-memory`: персистентное хранилище переписки — сессии, запись user/assistant-сообщений, восстановление контекста открытой сессии после рестарта, инструмент поиска по прошлым сессиям.

### Modified Capabilities

- `telegram-bot`: требование «Один длинный контекст на чат» меняется — история хранится персистентно в БД и переживает рестарты (сейчас: в памяти процесса, рестарт обнуляет); требование «Команда /new» меняется — команда закрывает сессию и начинает новую, а не стирает прошлое.

## Impact

- **Код**: `main.py` (замена `ChatHistories` на обращение к хранилищу, обработчики `/new` и текстовых сообщений), новый модуль хранилища, `tools.py` (+ инструмент `search_history` и его ToolSpec), системный промпт/скиллы (правила использования поиска по памяти).
- **Зависимости**: sqlite3 из stdlib или aiosqlite (решение в design.md); новый внешний сервис не вводится.
- **Инфраструктура**: путь к файлу БД настраивается через окружение с значением по умолчанию на VM-локальном диске; `scripts/sbx-*.sh` не требуют изменений, README дополняется.
- **Существующее поведение**: в пределах одной жизни процесса контекст LLM сохраняет инструментальный транскрипт текущей сессии; после рестарта восстанавливаются только user/финальные сообщения (осознанное следствие решения «храним только итог»).
