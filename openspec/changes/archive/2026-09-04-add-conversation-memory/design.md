## Context

Сейчас история диалога — in-memory `ChatHistories = dict[int, list[Message]]` в main.py: agent-loop дополняет список на месте (включая инструментальный транскрипт), `/new` обнуляет список, рестарт процесса теряет всё. Бот — единственный процесс с long-pollingом внутри sbx-VM; workspace репозитория маунтится в VM (сетевая ФС — SQLite поверх неё нестабилен из-за локов/WAL). Мотивация — см. proposal.md (Why).

## Goals / Non-Goals

**Goals:**

- Персистентность user/финальных assistant-сообщений с переживанием рестартов бота и пауз сандбокса.
- Сущность «сессия» как граница беседы; поиск по завершённым сессиям для агента.
- Минимальная новая зависимость и нулевая эксплуатация нового сервиса.

**Non-Goals:**

- Персистентность инструментального транскрипта (осознанно исключено — см. спеку).
- Postgres, мультиинстансность, репликация.
- Семантический поиск (embeddings), саммариизация старых сессий.
- Бэкап/экспорт переписки в UI (только ручное копирование файла, в README).

## Decisions

### D1: Движок — SQLite, доступ через aiosqlite

SQLite: один процесс-писатель, нулевая эксплуатация, FTS5 в запасе. Доступ — `aiosqlite` (тонкая обёртка над потоком): бот полностью асинхронный, записи идут на пути сообщения, блокировать event loop нельзя. Альтернатива — stdlib `sqlite3` + `asyncio.to_thread`: без новой зависимости, но каждый вызов обёртки вручную. Выбираем aiosqlite как идиоматичный минимум.

### D2: Файл БД на VM-локальном диске, путь через окружение

По умолчанию `~/.local/share/dev-helper-bot/memory.db` внутри VM (рядом с `~/.venv-devbot`), переопределяется `MEMORY_DB_PATH`. В workspace не размещаем: сетевой маунт ломает SQLite-локи и WAL. Режим WAL включаем при открытии. README фиксирует: полный сброс VM стирает память; ручной бэкап — `sbx exec devbot cp ...`.

### D3: Схема — две таблицы

```sql
sessions(id INTEGER PRIMARY KEY,
         chat_id INTEGER NOT NULL,
         started_at TEXT NOT NULL,   -- ISO 8601 UTC
         ended_at TEXT);             -- NULL = открытая сессия
messages(id INTEGER PRIMARY KEY,
         session_id INTEGER NOT NULL REFERENCES sessions(id),
         role TEXT NOT NULL CHECK (role IN ('user','assistant')),
         content TEXT NOT NULL,
         created_at TEXT NOT NULL);
CREATE INDEX idx_messages_session ON messages(session_id, id);
CREATE INDEX idx_sessions_chat ON sessions(chat_id, ended_at);
```

Альтернатива — одна таблица messages с chat_id и session-маркером: меньше join, но теряется вменяемая граница сессии и время её закрытия.

### D4: Канон в БД, эпемерный транскрипт в полёте

На каждое сообщение: `history = [system] + messages(открытой сессии из БД) + [новое user]`. Агентный цикл работает с этим списком и дополняет его инструментальным транскриптом — но тот живёт только в рамках обработки одного сообщения и в БД не попадает. Запись: user-сообщение — до запуска цикла; финальный assistant-ответ — после успеха. Обработку с ошибкой LLM оставляем как «user-сообщение без ответа» (отражает реальность); откат записи — лишняя сложность. In-memory кэш историй не держим: БД — единственный источник истины, запрос лёгкий.

### D5: /new закрывает сессию

`UPDATE sessions SET ended_at = now WHERE chat_id = ? AND ended_at IS NULL`. Следующее сообщение, не найдя открытой сессии, открывает новую (INSERT). Подтверждение пользователю не меняется.

### D6: search_history — LIKE-подстрока по завершённым сессиям

Инструмент с одним строковым параметром `query`. Поиск: `messages JOIN sessions WHERE sessions.chat_id = ? AND sessions.ended_at IS NOT NULL AND messages.content LIKE '%'||?||'%'` — только завершённые сессии (открытая и так в контексте LLM). Результат: до 10 выдержек по ~300 символов, каждая с датой сессии; ничего не найдено — явное сообщение об отсутствии. Ограничение: LIKE в SQLite регистрозависим для не-ASCII (русский ищется «как написано»). Альтернатива FTS5 (unicode61/trigram) отложена до практической необходимости — апгрейд локальный, интерфейс инструмента не меняется.

### D7: Модуль memory.py, жизненным циклом владеет main

Новый плоский модуль `src/dev_helper_bot/memory.py` (паттерн проекта: agent.py, sandbox.py, tools.py) с классом `MemoryStore`: `open/close`, `append_user`, `append_assistant`, `close_session`, `load_open_history`, `search_completed`. main открывает store при старте и закрывает в finally — как с песочницей (design D5 из add-docker-sandbox). В системный промпт добавляется короткая инструкция: «для вопросов о прошлых беседах используй search_history» — текстовым скиллом в `skills/`.

### D8: Переполнение контекста длинной сессии

Восстановление истории ограничивается хвостом: последние 50 сообщений сессии (конфигурируется константой). Спека требует передавать историю сессии; хвост — клапан безопасности для контекстного окна LLM, при типовых объёмах не активируется.

## Risks / Trade-offs

- [SQLite-файл на VM-локальном диске стирается полным сбросом VM] → задокументировано как осознанное ограничение; ручной бэкап через `sbx exec` в README.
- [LIKE-поиск слаб для русской морфологии и регистра] → задел на FTS5 без смены интерфейса инструмента.
- [user-сообщения без ответа накапливаются при сбоях LLM] → отражает реальную переписку; фильтр «без ответа» не нужен для поиска.
- [Отказ БД в рантайме] → исключение всплывает в обработчик aiogram, пользователь получает сообщение об ошибке — паттерн уже есть для LLMUnavailable.

## Migration Plan

Миграция данных не нужна: отсутствующий файл создаётся пустым при старте. Откат — вернуть код; оставшийся файл memory.db безвреден. Развёртывание: добавить aiosqlite в зависимости, обновить README (переменная `MEMORY_DB_PATH`, живучесть, бэкап).
