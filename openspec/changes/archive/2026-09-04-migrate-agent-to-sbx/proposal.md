# Proposal: migrate-agent-to-sbx

## Why

Бот-процесс сегодня живёт на хосте: полный доступ к файловой системе, токенам и хостовому Docker-демону. Цель — unattended-автономность агента: персистентное состояние (файлы и установленные пакеты переживают сообщения) внутри сильной гипервизорной границы Docker Sandboxes, где «YOLO внутри, стены снаружи», а хост не затрагивается вовсе.

## What Changes

- **BREAKING**: весь бот (long-polling, память чатов, агентный цикл, docker CLI) переезжает внутрь microVM Docker Sandboxes (`sbx`); на хосте остаются только LM Studio и sbx-прокси.
- **BREAKING**: жизненный цикл песочницы exec меняется с «контейнер на одно сообщение» на один долгоживущий контейнер-жилец на весь бот: файлы в `/work` и пакеты `pip --user` переживают сообщения и `/new` (который сбрасывает только контекст LLM).
- LLM на хосте достижим из VM как `host.docker.internal:1234` через sbx-прокси (разовая `sbx policy allow network localhost:1234`); единственный override окружения — явный `-e LLM_BASE_URL=…` в команде запуска.
- Токен Telegram приходит бесплатно через `load_dotenv()` из workspace-маунта `.env`; `.env` недоступен командам агента (граница доверия — контейнер-жилец), что закрывает сценарий prompt-инъекции с эксфильтрацией токена.
- Runbook оформляется скриптами: `scripts/sbx-setup.sh` (одноразовая подготовка VM: шаблон, python-venv, editable-установка) и `scripts/sbx-start.sh` (ежедневный запуск бота после ребута, логи в `/tmp/bot.log` внутри VM).
- Восстановление после ребута хоста — вручную (принятое ограничение): без launchd/автостарта.
- Обновление кода: правки на хосте видны мгновенно (passthrough + editable-установка), применение — рестарт процесса бота внутри VM.
- Текст окружения в системном промпте (`SANDBOX_ENV_LINE`) обновляется: состояние больше не умирает с сообщением.
- README: раздел запуска переписывается под sbx-сценарий.

## Capabilities

### New Capabilities

- `sbx-hosting`: размещение всего бота в microVM Docker Sandboxes — создание сандбокса с workspace-маунтом, сетевая связка с LLM на хосте (host.docker.internal + network policy), VM-локальный venv с editable-установкой, запуск/логи/обновление/сброс по runbook-скриптам, ручное восстановление после ребута.

### Modified Capabilities

- `docker-sandbox`: требование «Жизненный цикл песочницы на агентный цикл» заменяется на «Долгоживущий контейнер-жилец»: один контейнер на процесс бота, файловое состояние переживает сообщения и сброс контекста `/new`; сценарии «Состояние не переживает сообщение» и «Установленные пакеты доступны до конца сообщения» инвертируются; самовосстановление, sweep сирот, лимиты ресурсов и валидация окружения при старте сохраняются без изменений.

## Impact

- **Код**: `agent.py` (lifecycle песочницы выходит из `run_agent`), `main.py` (один executor на процесс бота, проброс в хендлеры), `sandbox.py` (семантика `stop()` — при завершении бота; пересоздание жителя при смерти), `skills.py` (текст `SANDBOX_ENV_LINE`).
- **Не меняется**: `config.py` (override через env), контракт `exec`-инструмента, лимиты контейнера (`--memory 512m --pids-limit 256 -u 1000 --cap-drop ALL`), агентный цикл (8 шагов, 30с таймаут).
- **Новое в репо**: `scripts/sbx-setup.sh`, `scripts/sbx-start.sh`.
- **Тесты**: docker-маркированные интеграционные тесты жизненного цикла — под долгоживущий житель; hermetic-набор — правки под новую передачу executor'а.
- **Инфраструктура**: требуется установленный `sbx` CLI (brew/docker-sbx), login, разовая network policy; Alpine-образ песочницы собирается приватным docker-демоном внутри VM при первом старте.
- **Риски**: `/work` растёт без ограничений (сброс — `sbx rm`); память чатов умирает с процессом бота (как сегодня); два неизвестных в CLI (`sbx create` базовый шаблон, способ поднятия остановленного сандбокса) закрываются спайк-задачами.
