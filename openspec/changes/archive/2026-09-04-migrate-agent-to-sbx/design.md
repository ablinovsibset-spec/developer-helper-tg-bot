# Design: migrate-agent-to-sbx

## Context

Сейчас бот-процесс целиком живёт на хосте; в Docker-контейнер уходит только инструмент `exec` (контейнер на одно сообщение, `SandboxExecutor` в `sandbox.py`, lifecycle встроен в `run_agent`). Ходовой LLM-сервер (LM Studio) остаётся на хосте — нужна Metal-ускоренность macOS. Мотивация переезда — proposal.md, Why: unattended-автономность с персистентным состоянием за гипервизорной границей Docker Sandboxes.

Ключевые ограничения среды Docker Sandboxes (docs.docker.com/ai/sandboxes):
- сандбокс = microVM со своим docker-демоном; workspace маунтится passthrough'ом по абсолютному пути хоста; всё внутри персистентно до `sbx rm`;
- сервисы хоста достижимы как `host.docker.internal` при разовой `sbx policy allow network localhost:<порт>`;
- процессы не переживают stop/start сандбокса (пакеты, образы и диски — переживают).

## Goals / Non-Goals

**Goals:**
- Персистентное состояние агента (файлы, `pip --user`) в пределах жизни контейнера-жителя.
- Токен Telegram и workspace вне досягаемости команд агента.
- Runbook как скрипты репозитория; ручная модель восстановления.

**Non-Goals:**
- Автозапуск после ребута хоста (launchd, systemd-юниты, kit-автостарт) — принято «вручную».
- Изменение лимитов агентного цикла: 8 шагов LLM, 30с таймаут exec — без изменений.
- Расписания/рутины без входящего сообщения, персистентность памяти чатов между рестартами бота.
- Template/kit кастомизация сандбокса — пакетов хватает персистентности самой VM.

## Decisions

### D1: Команды агента — долгоживущий контейнер-житель внутри VM
Один контейнер на процесс бота: create при первом exec после старта, `docker exec` на каждое сообщение, rm best-effort при завершении.
- Почему не «exec напрямую в VM»: команды выполнялись бы в среде бота — `.env` с токеном читаем; скиллы тянут внешний контекст (wttr.in, Habr RSS), prompt-инъекция с эксфильтрацией токена срабатывает на 100%. Контейнер-житель оставляет токен за границей.
- Почему не «контейнер на сообщение + volume»: volume сохранил бы только файлы, потеряв фоновые процессы и системные пакеты; больше движущихся частей при той же цели.
- Сохраняются харднинг-флаги: `--memory 512m --pids-limit 256 -u 1000 --cap-drop ALL`, без маунтов workspace.

### D2: Один житель на весь бот, не на чат
Бот по сути одноместный; N контейнеров на чать требуют сборки сирот и памяти VM без изолирующей выгоды для единственного пользователя. Следствие: `/new` сбрасывает только контекст LLM, состояние общее для всех чатов.

### D3: Связь с LLM — host.docker.internal, override явным `-e`
`LLM_BASE_URL=http://host.docker.internal:1234/v1` передаётся флагом `-e` в команде запуска бота (dotenv не перезаписывает существующие переменные — override гарантированно побеждает localhost из workspace-`.env`, откуда бесплатно приходит `TELEGRAM_BOT_TOKEN`).
- Почему не `/etc/sandbox-persistent.sh`: скрытое состояние, неочевидное через месяц.
- Почему не правка `.env`/дефолта в `config.py`: ломает host-режим запуска бота (rollback-путь) либо добавляет код для авто-детекта окружения.
- Разовая подготовка: `sbx policy allow network localhost:1234`.

### D4: Установка — editable, venv на VM-локальном диске
`default_skills_dir()` и `default_dockerfile_dir()` резолвятся через `Path(__file__).parents[2]` — обычная `pip install .` положила бы пакет в site-packages без `skills/` и `Dockerfile` рядом. Поэтому: `python3 -m venv ~/.venv-devbot && pip install -e <workspace>`.
- venv вне workspace: иначе каталог окружения появится в репо на хосте и каждый импорт пересечёт virtiofs; editable-ссылка даёт живые правки кода и скиллов (applied рестартом процесса бота — `load_skills` выполняется на старте).

### D5: Lifecycle executor'а переезжает из `run_agent` в `main`
Один `SandboxExecutor` создаётся и стартует в startup-последовательности бота (`prepare_sandbox_environment` остаётся: `docker info` → sweep сирот → ensure образ — теперь против демона внутри VM), пробрасывается в хендлеры и `run_agent`; `stop()` — в `finally` главного цикла. `run_agent` перестаёт владеть lifecycle (сегодня `agent.py:73-104`). Самовосстановление D6 прежнего дизайна (пересоздание + повтор команды один раз) сохраняется и становится ценнее — житель долгоживущий.

### D6: Запуск процесса и логи — setsid-фон внутри VM, `/tmp/bot.log`
Бот запускается `sbx exec -e LLM_BASE_URL=… devbot bash -c "cd <workspace> &&
setsid nohup ~/.venv-devbot/bin/python -m dev_helper_bot.main >> /tmp/bot.log
2>&1 < /dev/null &"`; просмотр — `sbx exec devbot tail -n 50 /tmp/bot.log`.
Логи VM-локальные: быстро, переживают рестарты бота в пределах жизни
сандбокса, не засоряют репо.

Уточнения по факту прогона (v0.39.0):
- `sbx exec -d` держит хостовый клиент до завершения процесса — для
  скрипта запуска не подходит; вместо него классическое отделение
  (`setsid nohup … &` с перенаправлением всех потоков): exec-сессия
  закрывается, процесс в VM живёт.
- **Автостоп сандбокса**: демон гасит runtime через ~30с после отключения
  последней exec-сессии («auto-stopped runtime after last session
  disconnected»); фоновый процесс бота сессией не считается, настройки
  отключения нет. Решение (согласовано с пользователем): `sbx-start.sh`
  открывает keepalive-сессию — фоновый `sbx exec devbot sleep infinity`
  на хосте (pid в `/tmp/dev-helper-bot-keepalive-<name>.pid`). Пока клиент
  жив — сандбокс и бот работают; смерть клиента (рибут хоста) → автостоп →
  ручной перезапуск скрипта. Пауза оформлена `scripts/sbx-stop.sh`
  (закрыть keepalive + pkill бота + `sbx stop`).

### D7: Runbook — скрипты `scripts/sbx-setup.sh`, `sbx-start.sh`, `sbx-stop.sh`
Setup: установка sbx/login и policy (подсказки), `sbx create --name devbot shell <workspace>` (шаблон из спайка 1.1), apt-установка python3-venv, python-venv и editable-пакет. Start: поднятие остановленного сандбокса, фоновый запуск бота (D6), keepalive-сессия, хвост лога. Stop: закрыть keepalive + pkill бота + `sbx stop`. Обновление кода: повторный `sbx-start.sh` (внутри — pkill + рестарт). Полный сброс: `sbx rm` + setup.

## Risks / Trade-offs

- [Рост `/work` без ограничений (контейнер больше не удаляется каждое сообщение)] → осознанно; лечение — периодический `sbx rm` + setup; per-container storage-квоты на Docker Desktop недоступны (известное ограничение прошлого дизайна).
- [Смерть контейнера-жителя теряет `/work`] → зеркалит сегодняшнюю потерю при каждом сообщении; самовосстановление пересоздаёт контейнер с чистым состоянием, бот не падает.
- [Память чатов умирает с процессом бота] → без изменений относительно текущего поведения; в scope не входит.
- [Латентность импортов через virtiofs (editable)] → virtiofs-кэш включён по умолчанию; venv VM-локальный (D4), через passthrough ходит только код самого пакета.
- [Первый запуск медленнее: сборка Alpine-образа приватным демоном VM] → разово в жизни сандбокса; ensure_image уже умеет это (D8 прошлого дизайна).
- [Семантика env у `sbx exec -d`/хранимых переменных сандбокса документирована частично] → доставляем всё явно (`-e` на команду, токен через `load_dotenv` из workspace), не полагаемся на хранимое окружение; проверяется спайком.

## Migration Plan

1. Спайки (закрывают Open Questions): исследование CLI `sbx` на реальном создании сандбокса.
2. Рефакторинг lifecycle (D5) + текст `SANDBOX_ENV_LINE` в `skills.py` (состояние персистентно).
3. Скрипты D7, README (раздел запуска под sbx, сценарии обновления/сброса).
4. Тесты: docker-маркированные — под долгоживущего жителя; hermetic — под новую передачу executor.
5. Опробование: setup → start → диагностический диалог (персистентность файла между сообщениями, недоступность `.env`, LLM через прокси).

Rollback: изменения кода обратно совместимы с host-запуском (исполнитель всё тот же docker CLI; на хосте демон хостовый) — `git revert` возвращает прежний режим, отдельного механизма отката не требуется.

## Open Questions

Закрыты спайками 1.1–1.3 (sbx CLI v0.39.0, реальный сандбокс `devbot`):

- **Шаблон «голой» VM (спайк 1.1)**: позиционный аргумент — агент `shell`:
  `sbx create --name devbot shell /path/to/workspace`. `shell` — официально
  задокументированный agent-less сандбокс («no pre-installed agent binary»),
  образ `docker/sandbox-templates:shell-docker` (Ubuntu 26.04 LTS, python3
  3.14, curl, docker CLI к приватному демону VM предустановлены).
  Неочевидное обязательное условие первого создания: одноразовая инициализация
  глобальной сетевой политики `sbx policy init <allow-all|balanced|deny-all>`
  (выбран `allow-all` — соответствует «YOLO внутри» и пропускает Telegram API,
  wttr.in, Habr, PyPI без перечисления правил).
- **Поднятие остановленного сандбокса (спайк 1.2)**: отдельной команды
  `sbx start` в CLI нет — `sbx exec` сам поднимает остановленный сандбокс
  («If the sandbox is stopped, it is started first»; наблюдали
  «Sandbox devbot started successfully» при `exec` после `stop`).
  Env у `sbx exec -d`: флаги `-e KEY=VALUE` доходят и до detached-процесса,
  и до прямой (не обёрнутой в `bash -c`) команды; файлы внутри VM переживают
  stop/start. Хранимые переменные сандбокса (`/etc/sandbox-persistent.sh`)
  не используются — всё нужное доставляем явно (см. D3, D6).
- **Достижимость LLM-хоста (спайк 1.3)**: после разовой
  `sbx policy allow network localhost:1234` запрос
  `curl http://host.docker.internal:1234/v1/models` из сандбокса возвращает
  список моделей LM Studio. Workspace смотрирован по абсолютному пути хоста
  (`/Users/aleksandr/projects/developer-helper-tg-bot`), `.env` присутствует
  и читается процессом бота (но не командами агента — их граница доверия
  внутриконтейнерная, D1).
