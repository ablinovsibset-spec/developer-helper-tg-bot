# Design: minimal-agent

## Context

См. proposal.md — Why. Отправная точка: aiogram-бот с одноходовым конвейером `handle_text → llm.complete(messages) -> str`, шов `LLMClient` в `dev_helper_bot.llm`, LM Studio на этой же машине (Mac, 24 ГБ) с загруженной `openai/gpt-oss-20b`. Probe'ом подтверждён контракт LM Studio: `reasoning` приходит отдельным полем и не нужен в истории; `content` пуст на tool-ходе; `finish_reason` различает `tool_calls`/`stop`; `arguments` — JSON-строка.

## Goals / Non-Goals

**Goals:**

- Минимальный агентный harness поверх существующего шва `LLMClient`, тестируемый фейками без сети.
- Один инструмент `exec` и один механизм скиллов, покрывающие оба типа из задания (A: инструкция к API, B: рутина).

**Non-Goals:**

- Allowlist пользователей, персистентность истории, авто-суммаризация/обрезка истории, параллельная изоляция циклов одного чата, показ трассы/reasoning, выбор скиллов моделью, streaming.

## Decisions

### 1. Native tool-calling вместо ReAct-протокола
gpt-oss-20b обучена под агентный tool-calling; probe подтвердил полный round-trip через LM Studio. ReAct (текстовый протокол `ACTION:`/`FINAL:`) отвергнут: его единственное преимущество — неизменность шва — не перевешивает менее надёжный парсинг свободного текста и дублирование протокола, которого модель не «знает» нативно.

### 2. Эволюция шва вместо замены
`LLMClient.complete(messages, tools=None) -> AssistantTurn`, где `AssistantTurn` — TypedDict (`content: str | None`, `tool_calls: list[ToolCall]`, `finish_reason: str`). `Message` расширяется опциональными ключами `tool_calls` (на assistant-ходах) и `tool_call_id` (на tool-ходах); `reasoning` из ответа сервера в `AssistantTurn` не попадает и в историю не пишется. Альтернатива «новый метод `chat()` рядом с `complete()`» отвергнута: два метода на одном шве размывают контракт; дефолт `tools=None` сохраняет одноходовую семантику для вызывающих, которым инструменты не нужны.

### 3. Цикл по `finish_reason`, лимит 8, пустой ход = финал
`agent.py` держит цикл: `while steps < 8: turn = llm.complete(history, tools); if turn.tool_calls: execute → append → continue; else: return turn.content`. `finish_reason == "stop"` или пустой `content` без `tool_calls` трактуется как финал (защита от «пустого» хода). При исчерпании — сообщение о лимите шагов. Лимит 8 — середина диапазона задания (5–10).

### 4. exec: `asyncio.create_subprocess_shell`, таймаут 30с, обрезка голова+хвост
`tools.py` объявляет JSON-схему инструмента и исполнитель. Результат собирается в текст tool-сообщения: код выхода, stdout, stderr; при таймауте — `asyncio.wait_for` + принудительное завершение процесса и текст «таймаут 30с». Вывод длиннее ~3000 символов режется на первые ~1500 и последние ~1500 с маркером о вырезанной середине. Битый JSON в `arguments` или отсутствие `command` — не исключение, а tool-сообщение с ошибкой разбора: модель видит ошибку и корректирует вызов. Оболочка shell (а не exec-массив) осознанно: задание требует универсальности (пайпы, `&&`, cURL-однострочники).

### 5. Скиллы: `skills/*.md` в корне, склейка при старте
`skills.py` при старте читает каталог, каждый файл — `## <имя файла>\n<содержимое>`, всё склеивается в секцию системного промпта. Никакого выбора/индексации: контекст 131k вмещает оба скилла. Каталог в корне репо, а не в пакете: скиллы — данные пользователя, а не код; редактируются без переустановки пакета.

### 6. Память: `dict[chat_id, list[Message]]` в памяти процесса
Хранилище — атрибут, внедрённый в aiogram-диспетчер (как сейчас `dp["llm"]`). Ключ — `message.chat.id`. Персистентности нет (non-goal, рестарт = новые чаты — заявлено в спеке telegram-bot). Обрезки истории нет: 131k контекста + обрезка вывода exec + `/new` как клапан.

### 7. `/new` отдельным хендлером, зарегистрированным раньше `F.text`
`dp.message.register(Command("new"))` до регистрации текстового хендлера — иначе `/new` уйдёт в агентный цикл как обычный текст. Подтверждение сброса — короткое сообщение; в историю команда не попадает.

### 8. UX цикла: «⏳ Готовлю ответ…» один раз, финал новым сообщением
Индикатор отправляется до старта цикла и остаётся (не редактируется и не удаляется): финал новым сообщением не ломает чанкинг длинных ответов `send_chunked`. Промежуточные шаги не показываются (решение по В2). `send_chat_action("typing")` не дублирует индикатор и не нужен.

### 9. Конфигурация: дефолты под gpt-oss, reasoning effort — строкой в системном промпте
`LLM_MODEL` по умолчанию `openai/gpt-oss-20b`; таймаут HTTP-клиента по умолчанию 120с (reasoning-модель отвечает дольше). Effort `medium` фиксируется строкой `Reasoning: medium` в начале системного промпта — документированная конвенция gpt-oss; в LM Studio настройка сервера не требуется.

## Risks / Trade-offs

- [Любой пользователь Telegram может выполнять команды на машине владельца] → Осознанно принято при разведке (домашка без allowlist). Митигируется заделом на будущее: allowlist добавляется как aiogram-middleware без изменения цикла.
- [LM Studio изменит формат reasoning/tool_calls между версиями] → Парсинг ограничен швом `openai_compat`; integration-тест на фейковом HTTP-сервере фиксирует ожидаемый формат; при смене сервера правится один модуль.
- [Раздувание контекста в долгих чатах] → Обрезка вывода exec (~3000 симв.), лимит шагов 8, `/new`; авто-тримм истории — non-goal, при упоре в контекст решение на уровне LM Studio (131k).
- [Два параллельных сообщения в одном чате гоняют общую историю] → Допустимо для домашки; aiogram обрабатывает апдейты последовательно, взаимное перемежение маловероятно; изоляция циклов — non-goal.
- [Зомби-процессы при таймауте exec] → `kill` процесса и группы при таймауте (`asyncio.wait_for` + `process.kill()`).
- [Скилл утренней рутины ссылается на утилиты, которых может не быть (например, CLI календаря)] → Фича агента: model получает stderr «command not found» и адаптируется либо сообщает об отсутствии инструмента пользователю.

## Migration Plan

1. Реализация по tasks.md; существующие тесты, утверждавшие одноходовость, переписываются на инвертированные (сохранение контекста, `/new`).
2. `.env.example`: `LLM_MODEL=openai/gpt-oss-20b`; README дополняется разделами об агентном режиме, `/new`, `skills/`.
3. Выкатка — запуск `python -m dev_helper_bot.main` на той же машине; отката не требует: старое поведение не используется ничем внешним; rollback = `git revert` одного изменения.

## Open Questions

- Точная формулировка текстов «⏳ Готовлю ответ…» и сообщения об исчерпании шагов — решается при имплементации, на поведение не влияет.
- Нужна ли пользователю краткая статистика шагов в финальном ответе (сколько exec-вызовов выполнено) — можно добавить позже без изменения спек.
