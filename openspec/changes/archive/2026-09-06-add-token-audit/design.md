# Design: add-token-audit

## Context

Телеметрия (change add-agent-observability) пишет `runs`/`llm_calls`/`tool_calls`
в SQLite; `ObservingClient` уже считает `prompt_chars` и `messages_count` на
каждый вызов, `obs-dashboard.py` — самодостаточный stdlib-скрипт. Базы с данными
нет: аудит Части 2 нечего считать, а на вопрос «какой тип контекста растёт»
схема не отвечает — разбивки промпта по ролям не существует. Агентный конвейер
соединён в `handle_text` (main.py): system prompt + `load_open_history` +
`run_agent` с песочницей Docker (долгоживущий контейнер, workdir `/work`,
вывод команд усекается `truncate_output`).

## Goals / Non-Goals

**Goals:**

- Разбивка промпта по ролям в каждом `llm_calls` — с обратной совместимостью.
- Воспроизводимый benchmark-харнесс, генерирующий телеметрию реалистичного
  микса сценариев, изолированный от боевых БД.
- Аудит-скрипт, отвечающий на четыре вопроса Части 2, с baseline-отчётом «до».

**Non-Goals:**

- Оптимизации потребления (Часть 3); здесь только измерение.
- Точный токенайзер: сохраняется оценка chars/4 для tool-выводов.
- Разделение «файлов» и прочих tool-выводов: файлы читаются через `exec`,
  атрибутируются в «Tool outputs» как документированное ограничение.
- Изменение агентного цикла, контракта LLMClient, Telegram-слоя.

## Decisions

### D1: `prompt_roles` — JSON-колонка в `llm_calls`

`ALTER TABLE llm_calls ADD COLUMN prompt_roles TEXT` c JSON
`{"system": …, "user": …, "assistant": …, "tool": …}` (символы). Заполнение —
в `ObservingClient.complete()` рядом с существующим `prompt_chars`: роли
известны из `messages`, отдельного доступа к клиенту не нужно.

Альтернатива — детальная таблица `llm_call_messages` (строка на сообщение):
отвергнута, аудиту нужны агрегаты по ролям, а не по сообщениям; 4 строки на
роль-группу против N строк на вызов, и миграция тяжелее. Формат JSON повторяет
паттерн `usage_raw`.

### D2: миграция — idempotent `ALTER TABLE` при `open()`

`TelemetryStore.open()` после `executescript(_SCHEMA)` проверяет
`PRAGMA table_info(llm_calls)` и добавляет колонку, если её нет. Старые записи
остаются `null` (absence ≠ 0 — тот же принцип, что и для usage). Новая схема
тоже попадает в `_SCHEMA`, чтобы свежие базы создавались сразу с колонкой.

Откат безопасен в обе стороны: старый код перечисляет колонки в INSERT явно и
с лишней колонкой в таблице совместим.

### D3: харнесс реплицирует конвейер `handle_text`, мимо aiogram

`scripts/obs-benchmark.py` собирает тот же конвейер из тех же модулей:
`build_system_prompt(load_skills())` → своя `MemoryStore` → `RunRecorder` +
`ObservingClient` → `run_agent` с `SandboxExecutor`. Отличие от `handle_text`
только в отсутствии Telegram-транспорта и chunking. Телеметрия бенчмарка
по форме неотличима от боевой — аудит работает по обеим.

### D4: изоляция бенчмарка — отдельные файлы БД и метка

Харнесс пишет в собственные файлы: `--db` (телеметрия) и `--memory-db`
(память сессий) с дефолтами вида `~/.local/share/dev-helper-bot/benchmark*.db`.
Прогоны помечаются фиксированной меткой (`OBS_LABEL` не берётся — своя константа
харнесса, чтобы env не «перекрашивал» бенчмарк). chat_id — константы сценариев.
Боевые `observability.db` и память не открываются на запись вовсе.

### D5: фикстура-проект — файлы в репо, доставка `docker cp`

Фикстура лежит в `scripts/fixtures/sample_project/` (маленький python-проект:
несколько модулей, тесты, README). Харнесс перед файловыми сценариями делает
служебный exec (гарантия контейнера-жильца), затем `docker cp` каталога в
`/work` поверх (с предварительным `rm -rf` внутри) — идемпотентность через
пересоздание. Имя контейнера харнесс узнаёт у исполнителя (мини-свойство).

Альтернатива — доставка base64-блоками через сам `exec`: не требует знания
имени контейнера, но гоняет килобайты через текстовый канал и ломается об
ограничения длины команды; `docker cp` проще и надёжнее.

### D6: `obs-audit.py` — самодостаточный stdlib-скрипт

Как `obs-dashboard.py`: `sqlite3`, фильтры `--db/--label/--since`, четыре
секции с ASCII-барами. Дашборд не трогаем — у него другая роль (агрегаты и
timeline), аудит отвечает на вопросы Части 2.

### D7: расчёты Q4 и межпрогонного слоя

Внутрипрогонно: `repeated = Σ input_tokens(i)` по всем вызовам, кроме
последнего; `new = total − repeated`. Формула опирается на append-only историю
(агент только дописывает), feedback-сообщения валидации её не ломают —
ре-отправка всё равно полная.

Межпрогонно: токены истории сессии в первом ходе каждого прогона оцениваются
как `(user_chars + assistant_chars)` из `prompt_roles` хода 1, /4. Это оценка
сверху — текущая задача пользователя входит в `user_chars` и не вычитается:
текст сообщений в телеметрии не хранится (и не должен). Погрешность мала
относительно накопленной истории и помечается в выводе как оценка.

### D8: маппинг ролей → типы контекста (Q3)

`system` → System prompt; `tool` → Tool outputs (вкл. файлы); `assistant` →
Conversation history; `user`/`assistant` в ходе 1 — загруженная история сессии,
`user` сверх неё — текущая задача. Тренд: доли типов по номеру хода, от
первого к последнему, усреднённые по прогонам.

## Risks / Trade-offs

- [Поставщик не отдаёт cached/reasoning-токены (LM Studio + gpt-oss)] →
  секции кэша в аудите честно «недоступно»; выводы строятся на input/output.
- [Недетерминированность LLM: сценарий даёт разные траектории] → это оценка,
  а не измерение: фиксированные промпты, несколько повторов, label для
  фильтрации; conclusions — по порядкам величин.
- [`truncate_output` усекает большие выводы до попадания в промпт] → это
  корректно для аудита: телеметрия меряет то, что реально дошло до модели.
- [Docker не запущен / LLM занят в момент харнесса] → понятные ошибки и
  ненулевой exit code (спека benchmark-harness).
- [Оценка chars/4 неточна для code/кириллицы] → погрешность одинакова «до» и
  «после», для сравнительного аудита достаточна (принцип D6 из
  add-agent-observability).

## Migration Plan

Деплой — обычный: при первом старте `open()` добавит колонку в существующую
боевую базу. Откат кода безопасен (D2). Харнесс и аудит — новые файлы,
отката не требуют.
