# token-audit Specification (delta)

## Purpose

CLI-аудит потребления токенов по БД телеметрии: отвечает на четыре вопроса
Части 2 задачи observability — какие инструменты и ходы съедают токены, какой
тип контекста растёт быстрее всего и какая доля входных токенов отправляется
повторно, — формируя baseline для оптимизаций.

## ADDED Requirements

### Requirement: Топ инструментов по токенам
Аудит SHALL агрегировать оценочные токены вывода инструментов по имени
инструмента за выбранный период и выводить ранжированный список с абсолютными
значениями, долей в процентах и ASCII-барами.

#### Scenario: Ранжирование
- **WHEN** в базе есть tool-вызовы с непустыми результатами
- **THEN** инструменты перечислены по убыванию вклада в токены с долями и барами

#### Scenario: Нет вызовов инструментов
- **WHEN** в отфильтрованных прогонах нет tool-вызовов
- **THEN** раздел выводит понятное сообщение об отсутствии данных

### Requirement: Самый дорогой ход
Аудит SHALL строить распределение входных токенов LLM-вызовов по номеру хода
(turn_number) по прогонам и выводить ход с наибольшим средним входным контекстом
с его величиной и динамикой роста контекста от хода к ходу.

#### Scenario: Определение самого дорогого хода
- **WHEN** в базе есть прогоны с несколькими LLM-ходами
- **THEN** вывод называет номер хода с наибольшим средним входом и его токены

#### Scenario: Одноходовые прогоны
- **WHEN** все прогоны содержат по одному LLM-ходу
- **THEN** вывод честно отражает отсутствие динамики, не выдавая артефакт

### Requirement: Рост типов контекста
Аудит SHALL использовать разбивку промпта по ролям сообщений из телеметрии
LLM-вызовов, отображая доли типов контекста — system prompt, сообщения
пользователя, история диалога (assistant), выводы инструментов (tool) — с
ASCII-барами и трендом доли по ходам прогона. Для сообщений ролей user и
assistant, присутствующих уже в первом ходе прогона, аудит SHALL относить их
к загруженной истории сессии, а не к текущей задаче. Содержимое файлов
отображается в составе выводов инструментов как документированное ограничение.
Для записей без разбивки по ролям раздел SHALL выводиться как недоступный,
а не как ноль.

#### Scenario: Доли типов контекста
- **WHEN** записи телеметрии содержат разбивку по ролям
- **THEN** вывод показывает доли типов контекста с барами и их изменение
  от первого хода к последнему

#### Scenario: История сессии против текущей задачи
- **WHEN** первый ход прогона содержит user/assistant-сообщения прошлых
  сообщений сессии
- **THEN** эти символы учтены в истории сессии, а не в текущей задаче

#### Scenario: Записи без разбивки
- **WHEN** все отфильтрованные LLM-вызовы созданы до появления разбивки
- **THEN** раздел сообщает о недоступности данных, не подставляя нули

### Requirement: Повторно отправляемые токены
Аудит SHALL считать по каждому прогону повторно отправленные входные токены
как сумму входных токенов всех LLM-вызовов, кроме последнего (при
append-only истории каждый ход ре-отправляет весь предыдущий промпт), и
выводить суммарно: всего входных, новой информации, повторной, с долей
повторной в процентах. Дополнительно аудит SHALL оценивать межпрогонный слой
повторов: входные токены первого хода каждого прогона, относящиеся к
загруженной истории сессии, как ре-отправку между прогонами одного чата.

#### Scenario: Расчёт повторов внутри прогона
- **WHEN** прогон содержит N LLM-вызовов с входными токенами
- **THEN** повторные токены прогона равны сумме входных токенов первых N−1
  вызовов, новая информация — разности итога и повторных

#### Scenario: Межпрогонный слой
- **WHEN** проконы одного чата образуют сессию из нескольких сообщений
- **THEN** вывод отдельно показывает оценку токенов истории, ре-отправляемой
  из прогона в прогон

### Requirement: CLI-поведение аудита
Аудит SHALL выполняться CLI-командой, читающей БД телеметрии без запуска
бота, с фильтрами по метке и дате и параметром пути к БД. Пустая база и
отсутствие файла БД SHALL выводить понятное сообщение, не трейсбек.

#### Scenario: Фильтрация по метке
- **WHEN** аудит запущен с фильтром метки бенчмарка
- **THEN** расчёт ведётся только по прогонам с этой меткой

#### Scenario: Пустая база
- **WHEN** БД не содержит прогонов под фильтры
- **THEN** команда завершается с понятным сообщением об отсутствии данных
