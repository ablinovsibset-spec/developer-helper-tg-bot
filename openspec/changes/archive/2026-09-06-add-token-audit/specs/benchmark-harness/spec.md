# benchmark-harness Specification (delta)

## Purpose

Воспроизводимая генерация телеметрии агентных прогонов: фиксированный набор
сценариев гоняется через агент с реальным LLM и Docker-песочницей в обход
Telegram, чтобы аудит потребления токенов и сравнения «до/после» опирались на
одинаковые данные.

## ADDED Requirements

### Requirement: Прямой прогон сценариев
Харнесс SHALL исполнять фиксированный набор сценариев, вызывая агентный цикл
напрямую (без Telegram-транспорта) с реальным LLM и исполнителем команд
Docker-песочницы, и SHALL записывать телеметрию каждого прогона. Набор
сценариев SHALL быть закодирован в самом харнессе: повторные запуски без
изменения кода выполняют один и тот же набор.

#### Scenario: Полный прогон набора
- **WHEN** харнесс запущен при доступном LLM и запущенном Docker
- **THEN** каждый сценарий даёт прогон в БД телеметрии со статусом завершения

#### Scenario: Недоступный LLM
- **WHEN** LLM-эндпоинт недоступен
- **THEN** харнесс завершается с понятной ошибкой, не создавая частичных прогонов

### Requirement: Сценарии реалистичного микса
Набор сценариев SHALL покрывать архетипы реального использования: задачу с
чтением файлов проекта в песочнице, команду с объёмным выводом, поиск по
истории бесед и многоходовую сессию из нескольких последовательных сообщений
в одном чате. Многоходовая сессия SHALL обрабатываться в рамках одной сессии
памяти: каждое следующее сообщение видит ответы на предыдущие.

#### Scenario: Многоходовая сессия
- **WHEN** сценарий из трёх сообщений выполнен
- **THEN** в БД телеметрии три прогона одного chat_id, и контекст каждого
  следующего прогона включает пользовательские и финальные
  assistant-сообщения предыдущих

#### Scenario: Файловая задача
- **WHEN** выполнен сценарий чтения файлов
- **THEN** прогона достаточно tool-вызовов `exec` для содержательного аудита
  вклада инструментов в промпт

### Requirement: Фикстура тестового проекта
Харнесс SHALL создавать в песочнице фикстуру — небольшой python-проект с
несколькими файлами исходного кода и падающими/проходящими тестами — до
прогона файловых сценариев. Создание фикстуры SHALL быть идемпотентным:
повторный запуск харнесса не ломает её состояние.

#### Scenario: Первый запуск
- **WHEN** харнесс запущен в чистой песочнице
- **THEN** фикстура-проект создана и файловые сценарии выполняются над ней

#### Scenario: Повторный запуск
- **WHEN** харнесс запущен повторно
- **THEN** фикстура остаётся рабочей, сценарии выполняются без ошибок среды

### Requirement: Изоляция БД бенчмарка
Харнесс SHALL писать телеметрию в отдельный файл БД, отличный от боевой базы
observability, задаваемый параметром или переменной окружения. Боевая база
MUST NOT изменяться прогонами харнесса. Прогоны харнесса SHALL помечаться
меткой (label) для фильтрации в аудит-скриптах.

#### Scenario: Отдельная база
- **WHEN** харнесс выполняет прогон
- **THEN** записи появляются только в указанной БД бенчмарка с меткой прогона

#### Scenario: Боевая база не затронута
- **WHEN** харнесс завершил полный цикл
- **THEN** файл боевой базы телеметрии не изменился
