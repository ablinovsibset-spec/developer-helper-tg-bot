# Design: add-docker-sandbox

## Context

Единственная точка порождения процессов — `exec_command` в `src/dev_helper_bot/tools.py`: `asyncio.create_subprocess_shell` на хосте. Агентный цикл (`agent.py`) про способ выполнения не знает; контракт «команда → stdout/stderr/exit_code/таймаут/обрезка» определён и проверяется тестами. Скиллы (`wttr-in-api`, `habr-feed`, `morning`) используют только `curl` и `python3` со stdlib — портабельны на Alpine. aiogram 3 по умолчанию обрабатывает апдейты конкурентно (`handle_as_tasks=True`): параллельные сообщения = параллельные агентные циклы.

## Goals / Non-Goals

**Goals:**

- Команды LLM исполняются в изолированном контейнере: без доступа к ФС хоста, с лимитами памяти/pid, non-root.
- Файловое состояние переживает шаги одного сообщения (до 8 tool-calls), умирает после финального ответа.
- Контракт инструмента `exec` для модели и Telegram-слоя не меняется.
- Дефолтный `pytest` проходит на машине без Docker.

**Non-Goals:**

- Контейнеризация самого бота, деплой на сервер, docker-in-docker.
- Изоляция сети (sandbox имеет исходящий интернет — нужен скиллам).
- Квоты на диск контейнера, лимит числа параллельных песочниц (см. Risks).
- Персистентность состояния между сообщениями, именованные volume.

## Decisions

### D1. Песочница только для `exec`; бот остаётся на хосте

Бот продолжает работать рядом с LM Studio (`localhost:1234`), контейнеризируется только исполнение команд. Альтернатива «весь бот в контейнере + exec через docker.sock» отвергнута: монтирование сокета демона даёт sandbox фактически root на хосте и обнуляет мотивацию изменения.

### D2. Жизненный цикл: контейнер на агентный цикл (B2)

`run_agent` создаёт песочницу перед первым шагом и удаляет её в `finally`. Файлы переживают шаги внутри сообщения, изоляция почти эфемерная, накладные расходы — один `docker create` на сообщение.

Альтернативы: B1 (контейнер на каждую команду) ломает многошаговые сценарии «скачай → обработай» — файл шага 2 невидим шагу 5; B3 (контейнер на чат до `/new`) требует уборки забытых контейнеров, лимитов и бухгалтерии, не нужной курсовому боту.

### D3. Вызов Docker — CLI через существующий async-subprocess паттерн

`docker create/start/exec/rm` как подпроцессы (`asyncio.create_subprocess_*`), ноль новых зависимостей, дебаг руками в терминале. Альтернативы: docker SDK (синхронный, требует offload в треды), Engine API поверх aiohttp (полностью async, но заметно больше кода ради внутренней детали).

### D4. Таймаут — busybox `timeout` внутри контейнера, async-страховка снаружи

Команда оборачивается в `timeout <N> sh -c "<cmd>"` внутри контейнера: признак таймаута — код 143 (busybox `timeout` завершает команду SIGTERM'ом, который пробрасывается как 128+15; 124 — семантика coreutils, оставлена на случай замены образа), форматированный результат для модели сохраняет признак «⏱ Таймаут». Причина: `killpg` убивает только локальный CLI-клиент `docker exec`, процесс внутри контейнера продолжает жить. Async-страховка (`wait_for` с бюджетом N + ~10 с запаса на накладные расходы) прикрывает зависание самого docker CLI.

### D5. Харднинг — умеренный набор

`--memory 512m --pids-limit 256 --cap-drop ALL -u 1000 --rm --label dev-helper-bot.sandbox=true`. Рутфс контейнера записываемый: модель может ставить пакеты «на лету» через `pip install --user` (образ включает `py3-pip`, `HOME=/work` направляет установки в `/work/.local`; PEP 668 отключён через `PIP_BREAK_SYSTEM_PACKAGES=1` — изоляция пакетов в эфемерной песочнице не нужна). `apk add` непривилегированному пользователю недоступен (база `/lib/apk/db` принадлежит root) — установки умирают вместе с песочницей, что считается фичей, а не дырой. Параноидальный вариант (read-only + tmpfs `/work`) отвергнут: ломает установку пакетов на лету, а противник — 20B модель с tool-calling, не APT-актор.

### D6. Смерть песочницы mid-loop — ленивое самовосстановление

Если `docker exec` падает с «No such container»: пересоздать песочницу, повторить команду один раз, продолжить. Никакой отчётности «что потеряно» — модель получает обычный текст ошибки/результата и справляется сама. Альтернатива «ронять цикл» отвергнута: редкое событие не должно губить до 7 оставшихся шагов; детальный учёт потерь — сверх-инженерия.

### D7. Сироты и уборка — label + sweep при старте

`--rm` убирает мёртвый контейнер силами демона; при старте бот делает `docker ps -q --filter label=dev-helper-bot.sandbox=true` → `docker rm -f` для трупов после SIGKILL бота. Имя контейнеру не назначается (id из вывода `docker create`), коллизий нет.

### D8. Startup: `docker info` → sweep → ensure image

Без демона бот не стартует (SystemExit с русским сообщением, в стиле `telegram_token()`). Образ: если `docker image inspect` не находит — собрать из Dockerfile в репо (Alpine + `curl` + `python3` + `py3-pip`). Dockerfile создаёт `/work` с владельцем 1000, `ENV HOME=/work`, exec с `-w /work` — иначе `-u 1000` без home ломает `pip --user`, git-конфиг, `__pycache__` (ловушка №1 всего изменения).

### D9. Тесты — шов вместо мока Docker

`run_agent`/инструмент получает инъектируемый исполнитель команд (protocol-подобный seam). Unit-набор проверяет поведение на двойнике; чистые функции (`truncate_output`, `format_result`) — напрямую. Реальные Docker-сценарии (создание/уборка/таймаут/самовосстановление) — отдельные тесты с маркером `docker`, дефолтно отключённые (`addopts = -m "not docker"` в `pyproject.toml`), запуск: `pytest -m docker`.

### D10. Системный промпт — строка про окружение

К промпту добавляется факт: команды выполняются в изолированном Alpine-контейнере, файлы живут до конца обработки текущего сообщения, `cd`/env между вызовами не сохраняются. Модель перестаёт ожидать macOS-хост и межсообщенческое состояние.

## Risks / Trade-offs

- [Сеть: bridge-gateway открывает хостовые сервисы на `0.0.0.0`] → Задокументировать в README (LM Studio слушает `127.0.0.1` — безопасен; Ollama по умолчанию `0.0.0.0:11434` — достижима из песочницы). Полное лечение потеряло бы интернет для скиллов.
- [Диск: пер-container квоты не работают на Docker Desktop] → Ущерб ограничен 30с таймаутом (~15 GB worst case на команду) и возвращается `--rm` после цикла; принято осознанно.
- [RAM-буфер вывода до обрезки] → Уже существует на хосте, не регрессия этого изменения; не лечим.
- [Параллельные песочницы: aiogram конкурентен, каждая до 512 MB] → Принято для курсового масштаба; точечное лечение — semaphore вокруг создания песочниц, задел на будущее.
- [Коды 125/126/127 неоднозначны (docker CLI vs команда)] → Различимы по stderr; модель самокорректируется по тексту ошибки.
- [Латентность: `docker create` ~0.5–1 с на сообщение, exec ~десятки мс] → Приемлемо для Telegram-бота; первая сборка образа при старте ~минута.
- [Docker CLI-процессы-зомби при страх-таймауте] → Существующий паттерн `start_new_session=True` + `killpg` сохраняется для локального CLI-клиента.

## Migration Plan

Изменение аддитивное: новый модуль песочницы + Dockerfile; `tools.py`/`agent.py`/`main.py` правятся на месте; миграций состояния нет. Откат — git revert, бот сразу возвращается к host-exec. Развёртывание: обновить рабочую копию, убедиться в наличии Docker, запустить бот (образ соберётся сам).
