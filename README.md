# developer-helper-tg-bot

Telegram-бот — минимальный автономный агент: пересылает сообщения пользователя локальной LLM, модель может выполнять консольные команды через инструмент `exec`, следует текстовым скиллам и ведёт диалог в рамках одного длинного контекста на чат.

## Возможности

- **Агентный цикл**: модель вызывает инструмент `exec` (консольные команды), получает результаты и продолжает рассуждение до финального ответа (не более 8 шагов LLM на одно сообщение).
- **Хостинг в Docker Sandboxes**: весь бот исполняется внутри изолированной microVM (`sbx`) — с собственным Docker-демоном, файловой системой и сетью; хост не затрагивается. LM Studio остаётся на хосте и доступна из VM как `host.docker.internal:1234`.
- **Docker-песочница команд с персистентным состоянием**: команды `exec` выполняются в долгоживущем Alpine-контейнере-жильце (один на процесс бота): созданные файлы и пакеты `pip install --user` переживают сообщения и сброс контекста `/new`. Секреты бота (`.env` с токеном) находятся за границей доверия — командам агента недоступны.
- **Скиллы**: каталог `skills/` — текстовые инструкции для агента (правила API wttr.in, Habr, поиск по памяти, утренняя рутина), автоматически встраиваются в системный промпт при старте.
- **Память диалога**: переписка каждого чата хранится персистентно в SQLite на VM-локальном диске сандбокса — сообщения пользователя и финальные ответы переживают рестарты бота и паузу сандбокса; `/new` закрывает сессию и начинает новую, прошлые остаются доступны инструменту `search_history` («что мы обсуждали…»).
- **Наблюдаемость (observability)**: каждый LLM-вызов и вызов инструмента логируется в отдельную SQLite-базу (`observability.db`) — токены по типам, виртуальная стоимость, тайминги, исходы; реестр прогонов (одно сообщение = один run) и CLI-дашборд с агрегатами и timeline прогона. Телеметрия best-effort: её сбой не влияет на ответы агента.
- **UX**: «⏳ Готовлю ответ…» на время цикла, финальный ответ отдельным сообщением, разбиение ответов длиннее 4096 символов.

## Требования

- Установленный [sbx CLI](https://docs.docker.com/ai/sandboxes/install/) (Docker Sandboxes): `brew install --cask sbx`
- Авторизация: `sbx login` (учётная запись Docker; разовая операция)
- Запущенный LLM-сервер с OpenAI-совместимым API на хосте:
  - [LM Studio](https://lmstudio.ai/) (по умолчанию `localhost:1234/v1`) с загруженной моделью с поддержкой tool-calling (например `openai/gpt-oss-20b` или `llama-3.2-3b-instruct`), или
  - [Ollama](https://ollama.com/) (`localhost:11434/v1`), или
  - любой облачный провайдер (OpenAI, vLLM и т.п.)

## Настройка

1. Скопируйте `.env.example` в `.env` и заполните `TELEGRAM_BOT_TOKEN` — токен из [@BotFather](https://t.me/BotFather). Файл живёт в корне репозитория и не коммитится.

2. При необходимости скорректируйте параметры LLM:

   | Переменная | По умолчанию | Описание |
   |---|---|---|
   | `LLM_PROVIDER` | `openai_compatible` | Провайдер (LM Studio, Ollama /v1, vLLM, OpenAI) |
   | `LLM_BASE_URL` | `http://localhost:1234/v1` | Адрес OpenAI-совместимого endpoint'а (для запуска внутри сандбока переопределяется скриптом запуска на `host.docker.internal`) |
   | `LLM_MODEL` | `openai/gpt-oss-20b` | Имя модели, обслуживаемой backend'ом |
   | `LLM_API_KEY` | — | Для облачных провайдеров; для локальных LM Studio / Ollama оставьте пустым |
   | `MEMORY_DB_PATH` | `~/.local/share/dev-helper-bot/memory.db` | Файл SQLite с памятью переписки (VM-локальный диск сандбокса; не размещайте в workspace-маунте — сетевая ФС ломает SQLite-локи/WAL) |
   | `OBS_DB_PATH` | `~/.local/share/dev-helper-bot/observability.db` | Файл SQLite с телеметрией прогонов (то же правило VM-локального диска) |
   | `OBS_PRICE_INPUT_PER_M` | `0.11` | Виртуальная цена входных токенов, $ за 1M (дефолт — цены запуска gpt-oss-20b в API OpenAI) |
   | `OBS_PRICE_OUTPUT_PER_M` | `0.60` | Виртуальная цена выходных токенов, $ за 1M; кэшированные токены считаются по цене входных |
   | `OBS_LABEL` | — | Метка всех прогонов процесса — для маркировки экспериментов «до/после» (фильтр дашборда `--label`) |

## Запуск бота (внутри сандбокса)

Жизненный цикл оформлен скриптами репозитория. Автозапуска после перезагрузки хоста нет — восстановление ручное (осознанное ограничение).

### Подготовка (одноразово)

```bash
sbx login                                   # авторизация в Docker (разово)
scripts/sbx-setup.sh
```

`sbx-setup.sh` добавляет разовую network policy для доступа к LLM-порту хоста, создаёт сандбокс `devbot` (шаблон `shell` — «голая» agent-less VM) с workspace-маунтом этого репозитория и ставит python-окружение: venv на VM-локальном диске (`~/.venv-devbot`) и editable-установку пакета. Повторный запуск безопасен.

### Ежедневный запуск (в т.ч. после ребута хоста)

```bash
scripts/sbx-start.sh
```

Скрипт поднимает остановленный сандбокс (если нужно), останавливает предыдущий процесс бота (если был), запускает бот в фоне с `LLM_BASE_URL=http://host.docker.internal:1234/v1`, открывает keepalive-сессию и показывает хвост лога. Токен Telegram бот читает из workspace-`.env`.

**Keepalive-сессия**: демон Docker Sandboxes останавливает сандбокс через ~30с после отключения последней exec-сессии — фоновый процесс бота сессией не считается. Скрипт удерживает сандбокс фоновым клиентом (`sbx exec devbot sleep infinity`, pid пишется в `/tmp/dev-helper-bot-keepalive-devbot.pid`). Пока этот процесс жив на хосте — бот работает; после ребута хоста он умирает, и сандбокс гасится (ручная модель восстановления: перезапустить `scripts/sbx-start.sh`).

Логи (внутри VM, переживают рестарты бота в пределах жизни сандбокса):

```bash
sbx exec devbot tail -n 50 /tmp/bot.log
```

### Обновление кода

Правки кода и скиллов на хосте видны сандбоксу мгновенно (workspace-маунт + editable-установка). Применение — рестарт процесса бота:

```bash
scripts/sbx-start.sh        # внутри VM: pkill старого процесса + запуск нового
```

Изменение зависимостей дополнительно требует переустановки пакета в venv сандбокса (venv живёт на VM-локальном диске и pyproject автоматически не подхватывается):

```bash
scripts/sbx-setup.sh        # идемпотентен: переиспользует сандбокс, обновляет venv
```

### Пауза

```bash
scripts/sbx-stop.sh         # закрыть keepalive, остановить бот и сандбокс (состояние сохраняется)
scripts/sbx-start.sh        # продолжить
```

### Полный сброс

```bash
sbx rm devbot               # удалить сандбокс со всем состоянием
scripts/sbx-setup.sh        # создать заново с чистого листа
```

## Архитектура размещения

```
┌─ хост macOS ──────────────────────────────────────────────┐
│  LM Studio :1234          sbx CLI, скрипты репозитория     │
│  workspace репозитория (passthrough-маунт, .env с токеном) │
└──────────────┬─────────────────────────────────────────────┘
               │ hypervisor-граница (network policy localhost:1234)
┌─ сандбокс devbot (microVM, шаблон shell) ──────────────────┐
│  процесс бота: long-polling, агентный цикл, docker CLI     │
│  ~/.venv-devbot (editable-установка пакета)                │
│  ~/.local/share/dev-helper-bot/memory.db (память чатов)    │
│  ~/.local/share/dev-helper-bot/observability.db (телеметрия) │
│  приватный Docker-демон VM                                 │
│  └─ контейнер-жилец: команды exec агента (Alpine, /work)   │
│     без маунтов workspace → .env недоступен командам       │
└────────────────────────────────────────────────────────────┘
```

- Связь с LLM: бот внутри VM обращается к `host.docker.internal:1234`; адрес передаётся явным `-e LLM_BASE_URL=…` при запуске и побеждает `localhost` из workspace-`.env` (dotenv не перезаписывает существующее окружение).
- Исходящий интернет (Telegram long-polling, скиллы wttr.in/Habr, PyPI) идёт через штатный egress-прокси сандбокса.

## Агентный режим

- Каждое сообщение пользователя запускает агентный цикл: модель может выполнять консольные команды инструментом `exec` (таймаут 30с, вывод обрезается до ~3000 символов) и искать по прошлым беседам инструментом `search_history`.
- Команды выполняются в долгоживущем Docker-контейнере-жильце: контейнер создаётся при первом exec после старта бота и живёт до его завершения (один на процесс бота, не на чат). Ограничения: `--memory 512m --pids-limit 256 --cap-drop ALL -u 1000`, без маунтов хостовой файловой системы.
- **Персистентное состояние**: файлы в `/work` и пакеты `pip install --user` переживают сообщения, границы агентных циклов и `/new`; сброс — только пересозданием контейнера (аварийная смерть с самовосстановлением) или полным сбросом сандбокса.
- Если контейнер-жилец умирает, бот прозрачно пересоздаёт его (с чистым состоянием) и повторяет команду один раз.
- `/new` закрывает текущую сессию чата: следующий запрос к LLM начинается с чистого контекста, а закрытая сессия остаётся в памяти переписки и доступна поиску `search_history`.
- На время цикла бот отправляет «⏳ Готовлю ответ…»; если за 8 шагов финальный ответ не получен — приходит сообщение об остановке по лимиту.

## Память диалога

Переписка хранится в SQLite (`aiosqlite`, режим WAL) — файл на VM-локальном диске сандбокса, по умолчанию `~/.local/share/dev-helper-bot/memory.db` (переопределяется `MEMORY_DB_PATH`; см. таблицу выше).

- **Что хранится**: сообщения пользователя и финальные ответы ассистента, сгруппированные в сессии; `/new` закрывает сессию, следующее сообщение открывает новую. Промежуточный инструментный транскрипт (вызовы `exec` и их вывод) в БД не пишется: он живёт только в рамках обработки одного сообщения.
- **Живучесть**: рестарт процесса бота (в т.ч. `scripts/sbx-start.sh` после ребута хоста) и пауза/возобновление сандбокса (`sbx-stop`/`sbx-start`) сохраняют переписку открытой сессии — контекст восстанавливается из БД (хвост до 50 сообщений). Полный сброс сандбокса (`sbx rm devbot`) стирает память — это осознанное ограничение, не сбой: бот начинает с чистой историей.
- **Поиск по прошлому**: инструмент `search_history` ищет подстроку по завершённым сессиям текущего чата (до 10 выдержек с датой), правила использования — скилл `skills/search-history.md`. Открытая сессия и так в контексте LLM, поиск её не затрагивает. Изоляция чатов: переписка одного чата недоступна из другого.
- **Бэкап (ручной)**: скопировать файл БД из VM на хост через workspace-маунт:

```bash
sbx exec devbot cp ~/.local/share/dev-helper-bot/memory.db ./memory-backup.db
# файл появится в корне workspace (репозитория) на хосте
```

### Остаточные риски песочницы

- **Диск**: рост `/work` жителя не ограничен квотой (per-container `--storage-opt` недоступны); лечение — периодический полный сброс сандбокса.
- **Смерть жителя** теряет файловое состояние `/work` — зеркалит потерю при пересоздании; бот не падает (самовосстановление).
- **Таймаут**: busybox `timeout` внутри контейнера завершает команду SIGTERM'ом; зависший docker-CLI прикрывает внешняя страховка «таймаут + 10с».

## Наблюдаемость (телеметрия прогонов)

Каждая обработка сообщения — прогон (run) в отдельной SQLite-базе телеметрии (`aiosqlite`, WAL, тот же паттерн, что у памяти; файл на VM-локальном диске, по умолчанию `~/.local/share/dev-helper-bot/observability.db`, переопределяется `OBS_DB_PATH`). Запись best-effort: любой сбой телеметрии логируется warning'ом и не прерывает обработку — наблюдение не может стать причиной отказа агента и не влияет на ответы модели и исполнение инструментов.

- **Что фиксируется**: каждый вызов LLM (момент, модель, длительность, номер хода, input/output/cached/reasoning-токены — чего поставщик не отдал, то `NULL`, а не ноль; число сообщений и размер промпта в символах; виртуальная стоимость) и каждый вызов инструмента (имя, размер аргументов/результата, оценка токенов результата ~chars/4, длительность, исход — включая отказ валидации с нулевой длительностью). Прогон закрывается статусом: успех / остановка по лимиту шагов / ошибка валидации ответа / ошибка LLM — с агрегатами по всем своим вызовам.
- **Виртуальная стоимость**: считается на момент записи по прайсу `OBS_PRICE_INPUT_PER_M` / `OBS_PRICE_OUTPUT_PER_M` ($ за 1M токенов; дефолт — цены запуска gpt-oss-20b в API OpenAI). Локальная модель реально стоит $0 — стоимость учётная, для сопоставимости экспериментов «до/после»; смена прайса историю не переписывает. Метка `OBS_LABEL` клеймится на все прогоны запуска.
- **Ротация**: автоматики нет (осознанно). Очистка — удалить файл БД при остановленном боте; при следующем старте он создастся заново.

### Дашборд

```bash
# агрегаты: прогоны, токены по типам, стоимость, средние на прогон,
# cache hit rate (или «недоступно», если поставщик не отдаёт кэш), топ инструментов
python scripts/obs-dashboard.py
python scripts/obs-dashboard.py --label baseline        # только прогоны с меткой
python scripts/obs-dashboard.py --since 2026-09-01      # прогоны с даты

# timeline конкретного прогона: ходы LLM и вызовы инструментов
# с токенами, стоимостью и длительностями
python scripts/obs-dashboard.py --run 42

# путь к БД: --db, иначе OBS_DB_PATH, иначе дефолт
python scripts/obs-dashboard.py --db /tmp/obs-copy.db
```

Дашборд читает БД синхронно (stdlib `sqlite3`), бот не нужен; пустая база и неизвестный `run_id` дают понятное сообщение, а не трейсбек.

## Скиллы

Скиллы — markdown-файлы в каталоге `skills/` в корне репозитория; имя файла без расширения — имя скилла. Все `.md`-файлы загружаются при старте и встраиваются в системный промпт (правки применяются рестартом бота внутри VM). Отсутствие или пустота каталога допустимы — бот стартует без скиллов.

В репозитории четыре скилла:

- `skills/wttr-in-api.md` (Тип А — инструкция к API): форматы запросов wttr.in через curl, компактный вывод, `?lang=ru`, ограничение частоты.
- `skills/habr-feed.md` (Тип А — инструкция к API): правила RSS-ленты Habr — верифицированная команда `curl | python3` для топ-статей за последние 24 часа, срез до 10 статей, чистка UTM-хвостов, HTML-ссылки в ответе.
- `skills/search-history.md` (Тип А — инструкция к инструменту): когда и как модель ищет по прошлым беседам инструментом `search_history` (вопросы «что мы обсуждали…», выбор поискового запроса, честный ответ при пустом результате).
- `skills/morning.md` (Тип B — рутина): утренняя сводка — погода в Минске (по правилам `wttr-in-api`) → топ-статьи Habr за сутки (по правилам `habr-feed`) → итоговая сводка до 4000 символов.

## Тесты

```bash
# внутри venv хоста (разработка) или ~/.venv-devbot внутри сандбокса
pytest                # дефолтный hermetic-набор: без сети, секретов и Docker
pytest -m docker      # интеграционные тесты песочницы (нужен запущенный Docker-демон)
```

Дефолтный набор не требует сети и секретов: LLM подменяется фейками, исполнитель команд — двойником без Docker. Docker-тесты проверяют жизненный цикл жителя: персистентность файлов/пакетов между сообщениями, удаление при завершении, самовосстановление, sweep и сборку образа.

```
  memory.py           SQLite-хранилище переписки (сессии, восстановление, поиск)
  telemetry.py        телеметрия прогонов (TelemetryStore, RunRecorder, ObservingClient)

  skills.py           загрузка skills/*.md в системный промпт
  config.py           настройки и фабрика LLM (пути БД, виртуальный прайс)
  llm/                подпакет доступа к LLM (контракт с tool-calling и usage)
skills/               текстовые скиллы агента (данные, не код)
tests/                тесты (unit/, integration/ — включая docker-маркированные)
Dockerfile            образ контейнера-жителя (Alpine + curl + python3)
scripts/              runbook-скрипты (sbx-setup.sh, sbx-start.sh, sbx-stop.sh)

```
