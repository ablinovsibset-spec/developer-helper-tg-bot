# developer-helper-tg-bot

Telegram-бот — минимальный автономный агент: пересылает сообщения пользователя локальной LLM, модель может выполнять консольные команды через инструмент `exec`, следует текстовым скиллам (каталог в system, тела через `get_skill`) и ведёт диалог в рамках одного длинного контекста на чат.

## Возможности

- **Агентный цикл**: модель вызывает инструменты `exec` (консольные команды) и `read_file` (постраничное чтение файлов: строки с номерами, потолок ответа ~1500 символов, подсказка «продолжай со строки N»), получает результаты и продолжает рассуждение до финального ответа (не более 8 шагов LLM на одно сообщение). Суммарные выводы инструментов удерживаются в рамках символьного бюджета (8000 симв. на прогон): при превышении старейшие сворачиваются в заглушку с размером и указанием повторить вызов.
- **Хостинг в Docker Sandboxes**: весь бот исполняется внутри изолированной microVM (`sbx`) — с собственным Docker-демоном, файловой системой и сетью; хост не затрагивается. LM Studio остаётся на хосте и доступна из VM как `host.docker.internal:1234`.
- **Docker-песочница команд с персистентным состоянием**: команды `exec` выполняются в долгоживущем Alpine-контейнере-жильце (один на процесс бота): созданные файлы и пакеты `pip install --user` переживают сообщения и сброс контекста `/new`. Секреты бота (`.env` с токеном) находятся за границей доверия — командам агента недоступны.
- **Скиллы**: каталог `skills/` — markdown с YAML frontmatter (`name`, `description`); в системный промпт попадают только имя и description, полное тело загружается инструментом `get_skill`.
- **Память диалога**: переписка каждого чата хранится персистентно в SQLite на VM-локальном диске сандбокса — сообщения пользователя и финальные ответы переживают рестарты бота и паузу сандбокса; `/new` закрывает сессию и начинает новую, прошлые остаются доступны инструменту `search_history` («что мы обсуждали…»).
- **RAG по документам пользователя**: загруженные в чат файлы (`.txt`, `.md`, `.docx`, `.pdf`) разбиваются на chunks, эмбеддятся и хранятся в отдельной SQLite-базе с расширением [sqlite-vec](https://github.com/asg017/sqlite-vec); агент достаёт релевантные фрагменты инструментом `search_documents` и указывает источник. Индекс личный: документы одного пользователя недоступны другому. Управление — `/documents` и `/delete <имя файла>`.
- **Наблюдаемость (observability)**: каждый LLM-вызов и вызов инструмента логируется в отдельную SQLite-базу (`observability.db`) — токены по типам, виртуальная стоимость, тайминги, исходы; реестр прогонов (одно сообщение = один run) и CLI-дашборд с агрегатами и timeline прогона. Телеметрия best-effort: её сбой не влияет на ответы агента.
- **UX**: «⏳ Готовлю ответ…» на время цикла, финальный ответ отдельным сообщением, разбиение ответов длиннее 4096 символов.

## Требования

- Установленный [sbx CLI](https://docs.docker.com/ai/sandboxes/install/) (Docker Sandboxes): `brew install --cask sbx`
- Авторизация: `sbx login` (учётная запись Docker; разовая операция)
- OpenAI-совместимый LLM-endpoint (дефолт — облачный [routerai](https://routerai.ru), нужен `LLM_API_KEY`):
  - облачный агрегатор / OpenAI / vLLM, или
  - локальный сервер на хосте: [LM Studio](https://lmstudio.ai/) (`host.docker.internal:1234/v1` из сандбокса) с моделью с поддержкой tool-calling, или [Ollama](https://ollama.com/) (`:11434/v1`)

## Настройка

1. Скопируйте `.env.example` в `.env` и заполните `TELEGRAM_BOT_TOKEN` — токен из [@BotFather](https://t.me/BotFather). Файл живёт в корне репозитория и не коммитится.

2. При необходимости скорректируйте параметры LLM:

   | Переменная | По умолчанию | Описание |
   |---|---|---|
   | `LLM_PROVIDER` | `openai_compatible` | Провайдер (routerai, LM Studio, Ollama /v1, vLLM, OpenAI) |
   | `LLM_BASE_URL` | `https://routerai.ru/api/v1` | Адрес OpenAI-совместимого endpoint'а (в сандбоксе `sbx-start.sh` запрашивает URL/модели/ключ интерактивно) |
   | `LLM_MODEL` | `openai/gpt-5.6-luna` | Имя модели финального ответа |
   | `LLM_API_KEY` | — | Для облачного дефолта обязателен; для локальных LM Studio / Ollama оставьте пустым (в промпте `sbx-start.sh` — ввод `-`) |
   | `MEMORY_DB_PATH` | `~/.local/share/dev-helper-bot/memory.db` | Файл SQLite с памятью переписки (VM-локальный диск сандбокса; не размещайте в workspace-маунте — сетевая ФС ломает SQLite-локи/WAL) |
   | `OBS_DB_PATH` | `~/.local/share/dev-helper-bot/observability.db` | Файл SQLite с телеметрией прогонов (то же правило VM-локального диска) |
   | `RAG_DB_PATH` | `~/.local/share/dev-helper-bot/rag.db` | Файл SQLite с индексом документов: документы, chunks, векторы (то же правило VM-локального диска) |
   | `EMBEDDING_MODEL` | `baai/bge-m3` | Модель эмбеддингов; задаётся отдельно от `LLM_MODEL` |
   | `EMBEDDING_DIM` | `1024` | Размерность векторов модели эмбеддингов; должна совпадать с моделью |
   | `EMBEDDING_BASE_URL` | — | Только для отдельного поставщика эмбеддингов; иначе наследуется `LLM_BASE_URL`. `sbx-start.sh` эту переменную не передаёт |
   | `EMBEDDING_API_KEY` | — | Только для отдельного поставщика эмбеддингов; иначе наследуется `LLM_API_KEY`. `sbx-start.sh` эту переменную не передаёт |
   | `RAG_MAX_UPLOAD_BYTES` | `5000000` | Лимит сырого размера загружаемого файла (проверяется до скачивания) |
   | `RAG_MAX_EXTRACT_CHARS` | `300000` | Лимит объёма извлечённого из документа текста |
   | `RAG_MAX_CHUNKS_PER_DOC` | `800` | Лимит числа chunks одного документа после разбиения |
   | `OBS_PRICE_INPUT_PER_M` | `0.11` | Виртуальная цена входных токенов, $ за 1M (учётная величина для сравнений «до/после», не прайс текущей дефолтной модели) |
   | `OBS_PRICE_OUTPUT_PER_M` | `0.60` | Виртуальная цена выходных токенов, $ за 1M; кэшированные токены считаются по цене входных |
   | `OBS_LABEL` | — | Метка всех прогонов процесса — для маркировки экспериментов «до/после» (фильтр дашборда `--label`) |
   | `OBS_WEB_PORT` | `8765` | Порт in-process веб-дашборда телеметрии (`http://127.0.0.1:8765/`); bind всегда loopback. Если порт занят, бот не стартует polling |
   | `OBS_WEB_HOST` | `127.0.0.1` | Host бинда дашборда. В сандбоксе `sbx-start.sh` переопределяет на `0.0.0.0` — иначе проброс `sbx ports` не достает до loopback VM |

## Запуск бота (внутри сандбокса)

Жизненный цикл оформлен скриптами репозитория. Автозапуска после перезагрузки хоста нет — восстановление ручное (осознанное ограничение).

### Подготовка (одноразово)

```bash
sbx login                                   # авторизация в Docker (разово)
scripts/sbx-setup.sh
```

`sbx-setup.sh` добавляет разовую network policy для доступа к LLM-порту хоста, создаёт сандбокс `devbot` (шаблон `shell` — «голая» agent-less VM) с workspace-маунтом этого репозитория и ставит python-окружение: venv на VM-локальном диске (`~/.venv-devbot`) и editable-установку пакета. Повторный запуск безопасен.

### Ежедневный запуск (в т.ч. после ребута хоста)

```bash
scripts/sbx-start.sh
```

Скрипт поднимает остановленный сандбокс (если нужно), **интерактивно запрашивает четыре параметра** — `LLM_BASE_URL`, `LLM_MODEL`, `EMBEDDING_MODEL` и `LLM_API_KEY`, — останавливает предыдущий процесс бота (если был), запускает бот в фоне с выбранными значениями через `-e`, открывает keepalive-сессию и показывает хвост лога. Токен Telegram по-прежнему из workspace-`.env`. Скрипт `.env` **не** переписывает — параметры действуют только на этот процесс.

**Enter×4 — облачный (платный) стек.** Дефолты в промптах: `https://routerai.ru/api/v1`, `openai/gpt-5.6-luna`, `baai/bge-m3`; дефолт ключа берётся из строки `LLM_API_KEY=` в workspace-`.env` (файл не `source`'ится). Значение ключа не показывается — только признак «задан / не задан». Если URL или модель уже экспортированы в shell до вызова скрипта — они показываются как pre-fill в `[…]`; для ключа экспортированное окружение тоже побеждает `.env`.

Облачный дефолт (Enter×4, ключ из `.env`):

```bash
scripts/sbx-start.sh
# LLM_BASE_URL [https://routerai.ru/api/v1]: ⏎
# LLM_MODEL [openai/gpt-5.6-luna]: ⏎
# EMBEDDING_MODEL [baai/bge-m3]: ⏎
# LLM_API_KEY [set]: ⏎
```

Локальный LM Studio — адрес и модель вводятся с клавиатуры; ключ из `.env` сбрасывается вводом `-`, чтобы облачный ключ не ушёл на локальный сервер:

```bash
scripts/sbx-start.sh
# LLM_BASE_URL [https://routerai.ru/api/v1]: http://host.docker.internal:1234/v1
# LLM_MODEL [openai/gpt-5.6-luna]: openai/gpt-oss-20b
# EMBEDDING_MODEL [baai/bge-m3]: ⏎
# LLM_API_KEY [set]: -
```

Другой порт на хосте (например Ollama) — тоже ввод URL с клавиатуры:

```text
LLM_BASE_URL [https://routerai.ru/api/v1]: http://host.docker.internal:11434/v1
```

Пин routerai на дешёвый тир — ввести строку модели (см. ниже). Альтернатива: заранее экспортировать `LLM_*` / `EMBEDDING_MODEL` в shell и нажать Enter×4 (pre-fill). После смены параметров нужен повторный `scripts/sbx-start.sh`.

### routerai: пин на дешёвый тир `openai/flex`

routerai обслуживает `openai/gpt-5.6-luna` пятью endpoint'ами с разными ценами (₽/1M входных токенов): `openai/flex` 11.26, `openai` (base) 22.51, `amazon-bedrock` 24.76, `openai/priority` 45.02. Дефолтная балансировка «стабильность → цена» в наших прогонах мигрировала трафик с flex на base после сетевого флапа провайдера — base вдвое дороже по входу/выходу, берёт надбавку +25% за запись кеша (28.13 против 22.51) и ни разу не отдал кеш-чтение, тогда как flex читает префикс-кеш по ~10% своей цены.

Поэтому конфигурация routerai фиксирует endpoint пином в строке модели (см. закомментированный блок в `.env.example`):

```
LLM_MODEL=openai/gpt-5.6-luna@provider=openai/flex&allow_fallbacks=false
```

- `@...` — часть имени модели (параметры роутинга агрегатора): передаётся поставщику как есть, код клиента не меняется.
- `allow_fallbacks=false` — жёсткий пин: роутер не может тихо увести трафик на дорогой base (именно это наблюдалось и что предотвращаем). Цена жёсткости — 404 при полной недоступности flex; такие временные сбои клиент ретраит (до 3 попыток, паузы 1с/3с), а постоянные 4xx падают сразу.
- Валидационный прогон на идентичной структуре трафика: **−47% фактического биллинга** против дефолтного роутинга (подробнее — `task/routerai-flex-otchet.md`).

Оговорки по экономике:

- Кеш — бонус, а не план: допуск кеша вероятностный (hit rate одного и того же префикса в замерах колебался от 0/8 до 77% за вызов), TTL — минуты.
- На вызовах без кеш-попадания действует надбавка за запись кеша (+25% к входной цене) — уже учтена в измеренных −47%.
- Дрейф цен контролируется по фактическому биллингу: провайдерское поле `usage.cost` сохраняется в телеметрии отдельной колонкой `billed_cost` (₽, как отдал поставщик), аудит Q5 выводит его сумму основной строкой, оценки по прайсу — следом с пометкой «оценка».

**Keepalive-сессия**: демон Docker Sandboxes останавливает сандбокс через ~30с после отключения последней exec-сессии — фоновый процесс бота сессией не считается. Скрипт удерживает сандбокс фоновым клиентом (`sbx exec devbot sleep infinity`, pid пишется в `/tmp/dev-helper-bot-keepalive-devbot.pid`). Пока этот процесс жив на хосте — бот работает; после ребута хоста он умирает, и сандбокс гасится (ручная модель восстановления: перезапустить `scripts/sbx-start.sh`).

Логи (внутри VM, переживают рестарты бота в пределах жизни сандбокса):

```bash
sbx exec devbot tail -n 50 /tmp/bot.log
```

### Обновление кода

Правки кода и скиллов на хосте видны сандбоксу мгновенно (workspace-маунт + editable-установка). Применение — рестарт процесса бота:

```bash
scripts/sbx-start.sh        # внутри VM: pkill старого процесса + запуск нового
```

Изменение зависимостей дополнительно требует переустановки пакета в venv сандбокса (venv живёт на VM-локальном диске и pyproject автоматически не подхватывается):

```bash
scripts/sbx-setup.sh        # идемпотентен: переиспользует сандбокс, обновляет venv
```

### Пауза

```bash
scripts/sbx-stop.sh         # закрыть keepalive, остановить бот и сандбокс (состояние сохраняется)
scripts/sbx-start.sh        # продолжить
```

### Полный сброс

```bash
sbx rm devbot               # удалить сандбокс со всем состоянием
scripts/sbx-setup.sh        # создать заново с чистого листа
```

## Архитектура размещения

```
┌─ хост macOS ──────────────────────────────────────────────┐
│  LM Studio :1234          sbx CLI, скрипты репозитория     │
│  workspace репозитория (passthrough-маунт, .env с токеном) │
└──────────────┬─────────────────────────────────────────────┘
               │ hypervisor-граница (network policy localhost:1234)
┌─ сандбокс devbot (microVM, шаблон shell) ──────────────────┐
│  процесс бота: long-polling, агентный цикл, docker CLI     │
│  ~/.venv-devbot (editable-установка пакета)                │
│  ~/.local/share/dev-helper-bot/memory.db (память чатов)    │
│  ~/.local/share/dev-helper-bot/observability.db (телеметрия) │
│  приватный Docker-демон VM                                 │
│  └─ контейнер-жилец: команды exec агента (Alpine, /work)   │
│     без маунтов workspace → .env недоступен командам       │
└────────────────────────────────────────────────────────────┘
```

- Связь с LLM: при старте `sbx-start.sh` запрашивает URL, chat-модель, модель эмбеддингов и ключ (дефолт — routerai + `openai/gpt-5.6-luna` + `baai/bge-m3`, ключ из `.env`); выбранные `LLM_*` и `EMBEDDING_MODEL` уходят явными `-e` и побеждают значения из workspace-`.env` (dotenv не перезаписывает существующее окружение). `EMBEDDING_BASE_URL` / `EMBEDDING_API_KEY` скрипт не передаёт.
- Исходящий интернет (Telegram long-polling, скиллы wttr.in/Habr, PyPI) идёт через штатный egress-прокси сандбокса.

## Агентный режим

- Каждое сообщение пользователя запускает агентный цикл: модель может выполнять консольные команды инструментом `exec` (таймаут 30с, вывод обрезается до ~3000 символов; файлы для чтения — инструментом `read_file`, не `cat`), постранично читать файлы инструментом `read_file` (`path`, опциональные `offset`/`limit` в строках; строки с номерами, потолок ответа ~1500 символов, подсказка «продолжай со строки N» при обрезке) и искать по прошлым беседам инструментом `search_history`.
- Контекст запроса собирается единым швом (`skills.build_request_messages`): системный промпт без даты/времени + загруженная история сессии + текущее сообщение, которому предпосылается контекстная строка «Текущие дата и время: …» (обновляется на каждое сообщение, в память не пишется). Префикс «системный промпт + история» байтово стабилен — провайдер может кэшировать его.
- Выводы инструментов удерживаются в рамках бюджета 8000 символов на прогон: при превышении старейшие сворачиваются в заглушку «[компакция: вывод обрезан, было N симв.; вызови инструмент повторно при необходимости]» — команды остаются в соседних assistant-сообщениях, диалог не компактируется.
- Команды выполняются в долгоживущем Docker-контейнере-жильце: контейнер создаётся при первом exec после старта бота и живёт до его завершения (один на процесс бота, не на чат). Ограничения: `--memory 512m --pids-limit 256 --cap-drop ALL -u 1000`, без маунтов хостовой файловой системы.
- **Персистентное состояние**: файлы в `/work` и пакеты `pip install --user` переживают сообщения, границы агентных циклов и `/new`; сброс — только пересозданием контейнера (аварийная смерть с самовосстановлением) или полным сбросом сандбокса.
- Если контейнер-жилец умирает, бот прозрачно пересоздаёт его (с чистым состоянием) и повторяет команду один раз.
- `/new` закрывает текущую сессию чата: следующий запрос к LLM начинается с чистого контекста, а закрытая сессия остаётся в памяти переписки и доступна поиску `search_history`.
- На время цикла бот отправляет «⏳ Готовлю ответ…»; если за 8 шагов финальный ответ не получен — приходит сообщение об остановке по лимиту.

## Память диалога

Переписка хранится в SQLite (`aiosqlite`, режим WAL) — файл на VM-локальном диске сандбокса, по умолчанию `~/.local/share/dev-helper-bot/memory.db` (переопределяется `MEMORY_DB_PATH`; см. таблицу выше).

- **Что хранится**: сообщения пользователя и финальные ответы ассистента, сгруппированные в сессии; `/new` закрывает сессию, следующее сообщение открывает новую. Промежуточный инструментный транскрипт (вызовы `exec` и их вывод) в БД не пишется: он живёт только в рамках обработки одного сообщения.
- **Живучесть**: рестарт процесса бота (в т.ч. `scripts/sbx-start.sh` после ребута хоста) и пауза/возобновление сандбокса (`sbx-stop`/`sbx-start`) сохраняют переписку открытой сессии — контекст восстанавливается из БД (хвост до 50 сообщений). Полный сброс сандбокса (`sbx rm devbot`) стирает память — это осознанное ограничение, не сбой: бот начинает с чистой историей.
- **Поиск по прошлому**: инструмент `search_history` ищет подстроку по завершённым сессиям текущего чата (до 10 выдержек с датой), правила использования — скилл `skills/search-history.md`. Открытая сессия и так в контексте LLM, поиск её не затрагивает. Изоляция чатов: переписка одного чата недоступна из другого.
- **Бэкап (ручной)**: скопировать файл БД из VM на хост через workspace-маунт:

```bash
sbx exec devbot cp ~/.local/share/dev-helper-bot/memory.db ./memory-backup.db
# файл появится в корне workspace (репозитория) на хосте
```

### Остаточные риски песочницы

- **Диск**: рост `/work` жителя не ограничен квотой (per-container `--storage-opt` недоступны); лечение — периодический полный сброс сандбокса.
- **Смерть жителя** теряет файловое состояние `/work` — зеркалит потерю при пересоздании; бот не падает (самовосстановление).
- **Таймаут**: busybox `timeout` внутри контейнера завершает команду SIGTERM'ом; зависший docker-CLI прикрывает внешняя страховка «таймаут + 10с».

## RAG по документам пользователя

RAG добавил зависимости (`sqlite-vec`, `sqlean.py`, `pypdf`, `python-docx`), поэтому после обновления кода до этой версии один раз выполните `scripts/sbx-setup.sh` — venv сандбокса лежит на VM-локальном диске и сам `pyproject.toml` не подхватывает (см. [Обновление кода](#обновление-кода)).

Пришлите боту файл (`.txt`, `.md`, `.docx`, `.pdf`) — он извлечёт текст, построит индекс и подтвердит готовность. Пока файл обрабатывается, одно статус-сообщение редактируется по шагам: извлечение → фрагменты → эмбеддинги (`k/N` на длинных документах) → готов. Дальше обычные вопросы: агент сам вызывает поиск по документам и отвечает с указанием источника (для PDF — со страницей).

```
/documents            # список ваших документов с числом фрагментов
/delete policy.pdf    # удалить документ вместе с его фрагментами и векторами
```

### Архитектура pipeline

Свой RAG, без фреймворков: каждый шаг виден в коде.

**Индексация** (`main.handle_document`, вне агентного цикла — модель в ней не участвует):

```
документ Telegram → проверка формата и размера → скачивание в память
  → извлечение текста (documents.extract_document; у PDF — карта страниц)
  → разбиение на chunks со span страниц (documents.chunks_from_text)
  → эмбеддинги батчами с прогрессом k/N (embeddings.embed)
  → запись documents + chunks + векторов + FTS одной транзакцией (DocumentStore.index_document)
```

**Retrieval** (`search_documents`, вызывается моделью по необходимости):

```
вопрос пользователя → агентный цикл → модель вызывает search_documents(query)
  → к query подмешиваются последние реплики открытой сессии
  → эмбеддинг запроса → vec KNN и FTS5 (оба с фильтром user_id)
  → Reciprocal Rank Fusion → лексический rerank → Top-K
  → фрагменты с именем файла и страницей PDF → ответ с «Источник: <файл>[, стр. N]»
```

Документы **не** подставляются в системный промпт целиком: поиск — инструмент, который модель вызывает сама. Так контекст не раздувается на каждом сообщении, а бот честно говорит «в документах этого нет», когда поиск пуст.

| Модуль | Ответственность |
| --- | --- |
| `documents` | Извлечение текста (txt/md/docx/pdf), карта страниц PDF, chunking, лимиты — чистые функции без I/O |
| `document_store` | Схема SQLite + sqlite-vec + FTS5, гибридный retrieve (RRF + rerank), `UserDocumentSearcher` |
| `embeddings` | Контракт `EmbeddingClient` и OpenAI-совместимый `POST /embeddings` |
| `main` | Обработчик загрузки, команды `/documents` и `/delete`, проводка `user_id` |

### Chunking

- **Размер** 800 символов, **перекрытие** 120 (~15%).
- Обе границы окна прижимаются к границам слов, поэтому фактические размеры плавают в пределах заданных — зато фрагмент не начинается и не кончается обрывком слова.
- Trade-off: слишком мелкие chunks теряют контекст абзаца (в фрагменте остаётся факт без условий его применения), слишком крупные размывают релевантность и дороже в эмбеддингах. 800/120 выбраны под политики и гайды, где смысловая единица — абзац; значения меняются через константы в `documents.py`.

### Эмбеддинги

- Модель по умолчанию **`baai/bge-m3`**, размерность **1024** — multilingual, что важно для русскоязычных документов.
- Endpoint и ключ по умолчанию те же, что у чата (`LLM_BASE_URL` / `LLM_API_KEY`): один адрес и один ключ на диалог и индексацию. `EMBEDDING_BASE_URL` / `EMBEDDING_API_KEY` нужны только если эмбеддинги берутся у другого поставщика.
- Модель эмбеддингов **не** наследуется от chat-модели: при старте `sbx-start.sh` её выбирают отдельно (`EMBEDDING_MODEL`, дефолт `baai/bge-m3`).
- Chunks эмбеддятся батчами (по 32) с прогрессом `k/N` в статус-сообщении; запрос поиска — отдельным вызовом.
- Недоступность провайдера — явная ошибка индексации в чат; переписка и агентный цикл при этом продолжают работать.
- **Смена модели ломает индекс**: у другой модели другая геометрия векторов. Бот ловит это на старте (`EMBEDDING_DIM` не совпадает с существующей таблицей) и просит удалить файл индекса. Порядок: остановить бота, удалить `rag.db`, загрузить документы заново.

### Retrieval: гибрид, RRF, rerank

- Векторный канал — **косинусное расстояние** (`distance_metric=cosine`): для эмбеддингов важно направление вектора, а не его длина.
- Текстовый канал — **FTS5** по тексту фрагментов, с тем же фильтром `user_id`. Нет FTS5 в sqlean — бот не стартует, как без sqlite-vec.
- Два канала отдают по 15 кандидатов, сливаются **Reciprocal Rank Fusion** (`1/(60+rank)`), затем лексический **rerank** (RRF + точное вхождение строки запроса + перекрытие токенов) без вызова чат-модели.
- **Top-K = 5**: хватает, чтобы собрать ответ с указанием источника, и не съедает бюджет вывода инструментов агентного цикла (8000 символов на прогон). Каждый фрагмент в ответе инструмента обрезается до 600 символов.
- **Conversation-aware**: к `query` модели подмешиваются последние реплики открытой сессии (user и assistant до текущего сообщения), чтобы follow-up вроде «а можно перенести их?» находил тот же документ, что и полный вопрос.
- Для PDF в результате инструмента и в «Источник:» указывается страница или диапазон (`стр. 17`, `стр. 16–17`); у txt/md/docx номер страницы не выдумывается.

### Хранение

SQLite + sqlite-vec (`aiosqlite`, режим WAL) — отдельный файл от переписки, по умолчанию `~/.local/share/dev-helper-bot/rag.db` (`RAG_DB_PATH`). Отдельная база потому, что у индекса другой lifecycle и своё расширение SQLite: эксперименты с векторами не должны рисковать памятью диалога.

```
documents(id, user_id, filename, file_type, created_at)   UNIQUE(user_id, filename)
chunks(id, document_id, chunk_index, text, page_start, page_end)
chunk_vectors USING vec0(chunk_id, embedding float[1024] cosine, user_id PARTITION KEY)
chunk_fts USING fts5(text, content='chunks', content_rowid='id')
```

- **Сырые файлы не хранятся**: после индексации остаются только текст фрагментов и векторы.
- **Повторная загрузка того же имени** заменяет прошлую версию: старые фрагменты и векторы удаляются, затем пишется новая версия — одной транзакцией.
- **Живучесть**: индекс переживает рестарт бота и паузу сандбокса; полный сброс сандбокса (`sbx rm devbot`) стирает его вместе с памятью.
- **Драйвер SQLite** для этой базы — `sqlean.py`, а не stdlib `sqlite3`: многие сборки CPython (в частности установщики с python.org) собраны без загрузки расширений, и на них `sqlite3` не может поднять sqlite-vec. `sqlean.py` несёт свою сборку SQLite с включённой загрузкой, поэтому индекс работает одинаково на хосте и в сандбоксе. Память и телеметрия остались на stdlib `sqlite3` — расширения им не нужны.
- Если расширение sqlite-vec не загрузилось или в SQLite нет FTS5, бот **не стартует** с понятной ошибкой: RAG — заявленная возможность, тихо работать без неё было бы нечестно.
- Схема существующего `rag.db` мигрирует при открытии: колонки страниц и FTS создаются без обязательного wipe (страницы у уже загруженных PDF появятся после повторной отправки файла).

### Безопасность и изоляция

- Владелец документа — Telegram `user_id` **отправителя**, а не чат: в группе у участников разные личные индексы (история переписки по-прежнему привязана к чату).
- `user_id` — PARTITION KEY векторной таблицы, то есть KNN физически выполняется внутри партиции владельца. Текстовый поиск (FTS) и гибридное объединение тоже фильтруют по владельцу — утечка не должна зависеть от одной реализации.
- Поиск, `/documents` и `/delete` работают только со своими документами; удалить или увидеть чужой файл нельзя.
- Содержимое документов уходит провайдеру эмбеддингов (при облачном endpoint'е). Для приватных документов используйте локальный embedding-сервер через `EMBEDDING_BASE_URL`.

### Ограничения

- **Нет OCR**: PDF-сканы без текстового слоя дают пустой текст и отклоняются как пустой документ.
- **Индекс не следит за источником**: изменили файл — пришлите его заново (то же имя заменит прошлую версию). Страницы PDF у старых загрузок появляются после повторной отправки.
- **Структура документа теряется**: таблицы `.docx` разворачиваются в строки `ячейка | ячейка`, разметка `.md` остаётся текстом.
- Лимиты по умолчанию: 5 МБ на файл, 300 000 символов текста, 800 фрагментов на документ.

### Evaluation dataset

`eval/` содержит корпус политик (`eval/documents/*.md`), набор вопросов с ожидаемым источником (`eval/rag_eval_dataset.json`, 8 вопросов) и датасет ядра агента (`eval/agent_eval_dataset.json`: jailbreak, отказ, память, `/new`, JSON-аргументы инструментов, открытые вопросы для судьи). Проверка попадания ожидаемого источника и самого факта в Top-K идёт **тем же гибридным retrieve**, что и инструмент поиска, и входит в дефолтный прогон тестов:

```bash
pytest tests/unit/test_rag_eval.py
```

Прогон герметичный — на детерминированном двойнике эмбеддингов (хешированный bag-of-words), без сети и ключей. Те же файлы можно прогнать через реальные эмбеддинги, подставив рабочий клиент.

## Наблюдаемость (телеметрия прогонов)

Каждая обработка сообщения — прогон (run) в отдельной SQLite-базе телеметрии (`aiosqlite`, WAL, тот же паттерн, что у памяти; файл на VM-локальном диске, по умолчанию `~/.local/share/dev-helper-bot/observability.db`, переопределяется `OBS_DB_PATH`). Запись best-effort: любой сбой телеметрии логируется warning'ом и не прерывает обработку — наблюдение не может стать причиной отказа агента и не влияет на ответы модели и исполнение инструментов.

- **Что фиксируется**: каждый вызов LLM (момент, модель, длительность, номер хода, input/output/cached/reasoning-токены — чего поставщик не отдал, то `NULL`, а не ноль; число сообщений и размер промпта в символах; виртуальная стоимость по прайсу и, если провайдер отдаёт поле стоимости в usage, фактическая — отдельной колонкой `billed_cost` в единицах поставщика, без конверсии) и каждый вызов инструмента (имя, размер аргументов/результата, оценка токенов результата ~chars/4, длительность, исход — включая отказ валидации с нулевой длительностью). Прогон закрывается статусом: успех / остановка по лимиту шагов / ошибка валидации ответа / ошибка LLM — с агрегатами по всем своим вызовам.
- **Виртуальная стоимость**: считается на момент записи по прайсу `OBS_PRICE_INPUT_PER_M` / `OBS_PRICE_OUTPUT_PER_M` ($ за 1M токенов; дефолт 0.11 / 0.60 — учётная величина для сопоставимости экспериментов «до/после», не прайс текущей дефолтной модели). Смена прайса историю не переписывает. Метка `OBS_LABEL` клеймится на все прогоны запуска.
- **Ротация**: автоматики нет (осознанно). Очистка — удалить файл БД при остановленном боте; при следующем старте он создастся заново.

### Дашборд

```bash
# агрегаты: прогоны, токены по типам, стоимость, средние на прогон,
# cache hit rate (или «недоступно», если поставщик не отдаёт кэш), топ инструментов
python scripts/obs-dashboard.py
python scripts/obs-dashboard.py --label baseline        # только прогоны с меткой
python scripts/obs-dashboard.py --since 2026-09-01      # прогоны с даты

# timeline конкретного прогона: ходы LLM и вызовы инструментов
# с токенами, стоимостью и длительностями
python scripts/obs-dashboard.py --run 42

# путь к БД: --db, иначе OBS_DB_PATH, иначе дефолт
python scripts/obs-dashboard.py --db /tmp/obs-copy.db
```

Дашборд читает БД синхронно (stdlib `sqlite3`), бот не нужен; пустая база и неизвестный `run_id` дают понятное сообщение, а не трейсбек.

### Веб-дашборд (in-process)

Пока бот отвечает в чате, на `http://127.0.0.1:8765/` живой веб-дашборд телеметрии — сводка агрегатов, список прогонов, timeline выбранного прогона и вкладка аудита потребления токенов (те же вопросы Q1–Q5, что CLI `obs-audit.py`). Дашборд поднимается в том же процессе, что и long-polling (aiohttp `AppRunner` на loopback), обновляется клиентским опросом раз в ~1.5 с; выбранный прогон не переключается автоматически на новый — только вручную из списка.

- **Страницы**: `/` (сводка), `/runs` (реестр), `/runs/{id}` (timeline), `/audit` (Q1–Q5); JSON `/api/*` с query-фильтрами `label`/`since`.
- **Порт**: дефолт `8765`, переопределяется `OBS_WEB_PORT`. Bind всегда `127.0.0.1` (loopback, без LAN).
- **Fail-fast**: если порт занят, бот **не** стартует polling и выводит понятную причину — наблюдение не должно тихо молчать. Сбой открытия БД телеметрии, наоборот, soft: бот и веб живут, страницы отдают «телеметрия недоступна».
- **Доступ из браузера на хосте при запуске в сандбоксе**: дашборд биндится на loopback *внутри* VM, поэтому `scripts/sbx-start.sh` автоматически публикует порт `sbx ports devbot --publish 8765:8765` — после старта открывайте `http://127.0.0.1:8765/` на хосте. При `scripts/sbx-stop.sh` сандбокс останавливается и порт освобождается.
- **CLI остаётся**: `obs-dashboard.py` и `obs-audit.py` не удаляются и не меняют контракт — это самодостаточные читатели той же БД.

### Бенчмарк-харнесс и аудит токенов

```bash
# воспроизводимая генерация телеметрии: фиксированные сценарии напрямую
# через агентный цикл (мимо Telegram), отдельная БД и память бенчмарка
python scripts/obs-benchmark.py                        # полный набор, метка 'benchmark'
python scripts/obs-benchmark.py --label optimized      # метка прогонов для сравнения «до/после»
python scripts/obs-benchmark.py --only files --only verbose   # только выбранные сценарии
python scripts/obs-benchmark.py --db /tmp/bm.db --memory-db /tmp/bm-mem.db

# аудит потребления токенов по метке: топ инструментов, дорогие ходы,
# типы контекста, повторные токены, стоимость с кэш-скидкой
python scripts/obs-audit.py --db ~/.local/share/dev-helper-bot/benchmark.db --label optimized
python scripts/obs-audit.py --label optimized --cached-price-multiplier 0.5
```

- **Метка прогона** (`--label`, дефолт `benchmark`) пишется в телеметрию каждого созданного прогона: прогоны «до» и «после» оптимизаций живут в одной БД и разделяются фильтром метки. Боевые `observability.db`/`memory.db` харнесс не открывает.
- **Автопроверки ответов**: финальные ответы сценариев проверяются автоматически (числовая задача — ожидаемое число в ответе; многоходовая — упоминание зафиксированных на раннем шаге сущностей; файловая — упоминание сути бага фикстуры); провал маркируется в выводе отдельно от статуса прогона.
- **Стоимость аудита (Q5) в два слоя**: основной — фактический биллинг поставщика (сумма `billed_cost` из телеметрии, ₽ как есть), когда провайдер его отдаёт; справочный — оценки по прайсу: сырая (все входные по полной цене, `--price-input-per-m`/`--price-output-per-m`) и эффективная с кэш-скидкой (`cached_tokens` по отдельному прайсу, `--cached-price-multiplier`, по умолчанию 0.25 × входного) с явной пометкой «оценка». Без фактических стоимостей (LM Studio) основной строкой — сырая оценка; без кеш-данных эффективная равна сырой с явной пометкой.
- Отчёты экспериментов: `task/observability-2-baseline.md` (baseline), `task/observability-3-otchet.md` (до/после оптимизаций) и `task/routerai-flex-otchet.md` (экономика routerai: дефолтный роутинг vs пин на flex).

## Скиллы

Скиллы — markdown-файлы в каталоге `skills/` в корне репозитория. Каждый файл
начинается с YAML frontmatter (`---` … `---`): обязательные поля `name`
(должно совпадать со stem файла) и `description` (что делает скилл и когда
применять). Тело — markdown после закрывающего `---`.

При старте бот загружает все `.md`-файлы (fail-fast при битом frontmatter).
В системный промпт попадает только каталог `name` + `description` и инструкция
вызвать `get_skill(name)`, когда description подходит к запросу; полные тела
в system не включаются. Отсутствие или пустота каталога допустимы — бот
стартует без скиллов. Правки применяются рестартом бота.

Инструмент `get_skill`: по имени из каталога возвращает тело скилла без
frontmatter (из in-memory набора, загруженного при старте; не через песочницу).
Неизвестное имя — текст ошибки модели, цикл не прерывается.

В репозитории четыре скилла:

- `skills/wttr-in-api.md` (Тип А — инструкция к API): форматы запросов wttr.in через curl, компактный вывод, `?lang=ru`, ограничение частоты.
- `skills/habr-feed.md` (Тип А — инструкция к API): правила RSS-ленты Habr — верифицированная команда `curl | python3` для топ-статей за последние 24 часа, срез до 10 статей, чистка UTM-хвостов, HTML-ссылки в ответе.
- `skills/search-history.md` (Тип А — инструкция к инструменту): когда и как модель ищет по прошлым беседам инструментом `search_history` (вопросы «что мы обсуждали…», выбор поискового запроса, честный ответ при пустом результате).
- `skills/morning.md` (Тип B — рутина): утренняя сводка — `get_skill` для `wttr-in-api` и `habr-feed` → итоговая сводка до 4000 символов.

## Тесты

```bash
# внутри venv хоста (разработка) или ~/.venv-devbot внутри сандбокса
pytest                # дефолтный hermetic-набор: без сети, секретов, Docker и живого LLM
pytest -m docker      # интеграционные тесты песочницы (нужен запущенный Docker-демон)
pytest -m live        # red team / отказ / память / latency / LLM-as-a-Judge
```

Дефолтный набор не требует сети и секретов: LLM и эмбеддинги подменяются фейками (у эмбеддингов — детерминированные векторы, поэтому retrieval проверяется на релевантности), исполнитель команд — двойником без Docker, индекс документов — файлом в `tmp_path`. Docker-тесты проверяют жизненный цикл жителя: персистентность файлов/пакетов между сообщениями, удаление при завершении, самовосстановление, sweep и сборку образа.

`pytest -m live` ходит в реальный chat-endpoint из env (`make_llm()`, как у бота) для red team, отказа, памяти и latency. LLM-as-a-Judge всегда бьёт в агрегатор `https://routerai.ru/api/v1`, а не в `LLM_BASE_URL` бота: субъект `openai/gpt-5.6-luna` (`JUDGE_SUBJECT_MODEL`), судья `openai/gpt-5.6-sol` (`JUDGE_MODEL`). Нет ключа или LLM недоступен — соответствующие тесты `skip`, дефолтный `pytest` от этого не падает.

| Переменная | Дефолт | Назначение |
|---|---|---|
| `LLM_API_KEY` | — | Ключ клиента: live red team/latency через `make_llm()` и оба вызова судьи |
| `JUDGE_SUBJECT_MODEL` | `openai/gpt-5.6-luna` | Модель, которая отвечает на открытые вопросы судьи |
| `JUDGE_MODEL` | `openai/gpt-5.6-sol` | Модель-судья (вежливость / точность / краткость, среднее ≥ 0.8) |
| `LIVE_FULL_SECONDS` | `4` | Порог полного `complete()` короткого пинга |
| `LIVE_TTFT_SECONDS` | `1.5` | Порог TTFT по SSE-зонду `stream=true`; нет streaming — skip только этого теста |
